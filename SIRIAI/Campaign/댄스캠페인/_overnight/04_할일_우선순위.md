## 주요 리스크 (알고만 있어도 절반은 막힙니다)

**R1. 🔴 마스터시트 열 오염 — 조용히, 성공한 것처럼 데이터를 파괴함**
LUN8 시트에 브릿지를 붙이고 스캔·편집을 하면 **엉뚱한 열이 덮어써집니다.** 이유: 헤더 자동인식이 공백 제거 후 **정확일치**만 잡는데 LUN8 헤더는 `틱톡 조회수`·`틱톡 콘텐츠①`처럼 플랫폼 접두어가 붙어 있어 매칭에 실패하고, 실패하면 **에러 없이 베이온 열번호로 폴백**합니다. 더욱이 `팔로워`·`가드닝대상여부` 열은 LUN8에 **아예 없어** 5·6열(이메일/연락처 영역)로 폴백합니다. 되쓰기 좌표는 아직 전부 하드코딩이고(브릿지는 field를 받을 준비가 됐지만 **부르는 쪽이 하나도 없음**), 수동잠금 보호도 우회됩니다.
→ **대응: D-day 전 배포 금지. 배포하더라도 읽기만, 그리고 `colmap`을 먼저 육안 검증(1분).** 44명 데이터를 손으로 복구하는 사고는 며칠 뒤에나 발견됩니다.

**R2. 🔴 정산 공식 미확정이 안내문을 막고, 안내문이 D-day를 막음** — 유일한 진짜 임계경로
0-2와 0-3이 안 풀리면 1-2를 못 씁니다. **이건 코드가 아니라 계약이라 개발로 우회 불가.** 특히 마루 6,000엔이 "마루에 주는 돈"인지 "마루 크리에이터에게 주는 돈"인지에 따라 **원가가 2배** 차이납니다.

**R3. 🟠 납품시트 인스타 행이 조용히 전부 사라짐** — 설계대로 만들면 100% 발생
자동 납품 함수는 ①헤더가 맞는 **첫 번째 탭만** 찾아 씁니다(탭 인자 없음 → 인스타가 틱톡 탭에 섞임) ②중복키를 `@핸들`로 뽑는데 **인스타 URL엔 @가 없어** 모든 인스타 행이 조용히 버려집니다. 오류도 안 나고 `added: 0`만 돌아옵니다. ③검수 통과 조건이 3열 전부 pass인데 LUN8은 검수 2열이라 그대로면 **0건**.
→ **대응: 이번 캠페인 자동 납품 사용 금지. 수기 복붙.**

**R4. 🟠 정원 부족 — 도구가 아니라 사람이 모자랄 가능성**
44명(시리아이만)으로 100건. 1인 1건이면 **56건 부족**, 1인 2플랫폼이어도 드랍 20~30% 감안 시 마루 없이는 미달. **마루 인원수를 모르는 채로 시간이 흐르는 게 진짜 위험**입니다. 7/22 이후엔 추가 모집해도 업로드 시간이 안 남습니다.

**R5. 🟠 인스타 50건이 조용히 방치됨** — 가장 유력한 실패 시나리오
자동화 0이라 "아무도 안 보고 있었다"가 실제로 일어나는 구성. 마지막 3일에 발견하면 수정 요청할 시간이 없어 그대로 미달. → 0-6 폼 + 0-10에서 **이름을 적어** 담당 지정.

**R6. 🟡 검수 3종 조건을 크리에이터가 모른 채 촬영**
납품 자격은 음원·구간·해시태그 **전부 pass**. 안내가 늦으면 대량 탈락 → 재촬영 → 이탈. **7/22에 이미 찍은 영상은 못 고칩니다.** → 1-2를 하루 앞당기는 게 가장 확실한 수율 방어.

**R7. 🟡 스캔·집행이 대표 PC 1대에 묶여 있음 (구조적)**
스캔·가드닝 집행·납품이 전부 `LOCAL_ONLY`. 팀원은 조회·편집만 가능. **대표님이 하루 빠지면 그날 틱톡 갱신과 가드닝이 멈춥니다.** 6일 안에 구조는 못 바꾸니, "멈춰도 캠페인이 안 죽는다"(수집은 폼, 검수는 팀원)로 설계를 짜두는 게 대응책.

**R8. 🟡 돈은 코드상 이미 잘 잠겨 있음 — 위험은 사람 쪽**
클라우드에 API 키 없음, 비번 게이트(상수시간 비교), 중복주문 차단(`inFlight`), 주문번호 없으면 배치 중단 — 안전장치는 충분합니다. **실제 위험은 ①미검증 인스타 서비스에 첫 지출(→0-8로 회피) ②105건 초과 시 배제 규칙 부재(→0-3)** 두 개뿐이고 둘 다 결정 문제입니다.

**R9. 🟡 Apps Script 6분 제한**

**R11. 🔴 지정 음원이 인스타에서 안 되거나, 됐는지 확인이 안 됨** — 캠페인 절반의 전제
