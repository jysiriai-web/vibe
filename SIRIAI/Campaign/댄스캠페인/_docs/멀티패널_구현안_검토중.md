# 두 패널(플랫폼별 SMM) 도입 구현안

조사 결과는 확인했고, **지적하신 폴링 위험은 코드로 확인됩니다**. `src/orders.js:29`의 `refreshOrders(smm, orders)`는 클라이언트를 하나만 받고 34행에서 `smm.multiStatus(active.map(o => o.id))`로 미완료 주문 전체를 한 패널에 던집니다. 레코드에 패널 칸이 없어(`data/c/lun8/orders.json`·`data/c/bayonn/orders.json` 전체 키 집합에 `panel` 없음 — node로 확인) 걸러낼 근거조차 없습니다. 겹치면 42행 `statuses[String(o.id)]`가 남의 상태를 우리 것으로 승격시키고, 안 겹치면 43행 `continue`로 remains가 주문 당시 값에 영구 고정됩니다. 둘 다 나쁜데 전자는 이중지출, 후자는 그 계정 영구 차단입니다.

## 1. Config 모양 — 먼저 확정

### 1-1. 왜 이 모양인가

세 가지 제약이 모양을 결정합니다.

- **키는 `.env`에만.** `campaigns.json`은 `scripts/make-vercel-env.js`가 통째로 `CAMPAIGNS_JSON` 환경변수로 만들어 Vercel에 올립니다(43~47행). 여기에 키를 넣으면 클라우드에 키가 올라가고, "클라우드엔 키가 없어서 URL을 아는 누구도 지출을 못 한다"(`src/cloud.js:2-4`)는 방어선이 무너집니다.
- **URL은 비밀이 아니므로 config에.** 패널 주소는 어느 패널인지 사람이 읽어야 하는 값입니다. `src/smm.js:17`의 `process.env.SMM_API_URL` 전역 폴백은 **제거해야 합니다** — 지금 `createSmm(realsiteKey)`를 url 없이 부르면 realsite 키가 smmkings로 나갑니다. 응답은 `kind:'panel'` 거절이라 `src/execute-core.js:156-158`이 그 계정만 조용히 건너뜁니다. 이 저장소가 가장 경계하는 모양입니다.
- **panels가 없으면 지금 그대로.** 새 키가 config에 없을 때 코드가 만드는 것은 `{smmkings}` 하나뿐이어야 합니다.

### 1-3. 환경변수 이름 규칙

패널 id에서 기계적으로 유도합니다. 사람이 `keyEnv` 같은 걸 또 적으면 그게 어긋나는 날이 옵니다.

```
SMM_KEY_<패널ID를 대문자로, 영숫자 아닌 건 _>      예) SMM_KEY_SMMKINGS, SMM_KEY_REALSITE
SMM_URL_<같은 규칙>                                 (선택 — config 의 url 이 우선)
```

**하위호환 규칙(중요):** 기본 패널(`smmkings`)에 한해 `SMM_KEY_SMMKINGS`가 없으면 기존 `SMMKINGS_API_KEY`를, `SMM_URL_SMMKINGS`도 config url도 없으면 기존 `SMM_API_URL` → `DEFAULT_URL` 순으로 폴백합니다. **지금 `.env`를 한 글자도 안 고쳐도 됩니다.** 두 번째 패널만 새 이름을 씁니다.

`.env.example`에 추가(값은 비운 채):

```diff
 # smmkings.com API 키 (계정 → API 페이지에서 발급)
 SMMKINGS_API_KEY=
+
+# ── 패널이 둘 이상일 때 ──
+# 이름 규칙: SMM_KEY_<패널ID 대문자>  (패널ID 는 campaigns.json 의 panels 키)
+# 기본 패널(smmkings)은 위 SMMKINGS_API_KEY 를 그대로 씁니다 — 안 바꿔도 됩니다.
+#SMM_KEY_REALSITE=
```

### 1-4. "패널 하나면 지금과 동일" 증명

| 지금 | panels 1개일 때 새 코드 | 같은가 |
|---|---|---|
| `key = CLOUD ? null : process.env.SMMKINGS_API_KEY` | `keyOf('smmkings')` = `SMM_KEY_SMMKINGS ?? SMMKINGS_API_KEY`, CLOUD면 `noKeys` | ✅ 같은 문자열 |
| `createSmm(key)` → url = `SMM_API_URL ?? DEFAULT_URL` | `createSmm(key, urlOf('smmkings'))` = `config.url ?? SMM_URL_SMMKINGS ?? SMM_API_URL ?? DEFAULT_URL` | ✅ 같은 URL |
| `const smm` (모듈 전역 1개) | `PANELS.clientOf(defaultId)` — 레지스트리가 캐시한 **같은 인스턴스** | ✅ 동일 객체 |
| `serviceOf(c)` = `findService(catalog(), 3693)` | `serviceOf(c,'tk')` = `findService(catalog('smmkings'), 3693, 'smmkings')`, 파일 폴백 = `data/smm-services.json` | ✅ 같은 서비스 객체 |
| 나가는 HTTP | 같은 url·같은 params·같은 순서 | ✅ (검증법 §7-B) |

`services`가 없어도 `normalizeServices`가 `serviceId`를 `{tk:{panel:기본,service:3693}}`로 승격하므로, **`campaigns.json`을 아예 안 고쳐도 동작이 같습니다.** 위에 `panels`/`services`를 적어두는 건 "명시가 폴백보다 낫다"는 이유 하나뿐입니다.

```js
// SMM 패널 레지스트리 — "어느 패널로 사는가"를 여기 한 곳에서만 정한다.
// panels 가 없으면 smmkings 하나 = 지금과 완전히 같은 구성.
import { createSmm } from './smm.js';

export const DEFAULT_PANEL = 'smmkings';
const FALLBACK_URL = 'https://smmkings.com/api/v2';
const env = (id, kind) => 'SMM_' + kind + '_' + String(id).toUpperCase().replace(/[^A-Z0-9]/g, '_');

const keyOf = (id) =>
  process.env[env(id, 'KEY')] || (id === DEFAULT_PANEL ? process.env.SMMKINGS_API_KEY || '' : '');
const urlOf = (id, def) =>
  (def && def.url) || process.env[env(id, 'URL')] ||
  (id === DEFAULT_PANEL ? (process.env.SMM_API_URL || FALLBACK_URL) : '');

const cache = new Map(); // `${id}|${url}` → 클라이언트. 같은 패널은 언제나 같은 인스턴스.

export function buildPanels(cfgPanels, { noKeys = false } = {}) {
  const defs = cfgPanels && Object.keys(cfgPanels).length ? cfgPanels : { [DEFAULT_PANEL]: {} };
  const ids = Object.keys(defs);
  const list = ids.map((id) => {
    const url = urlOf(id, defs[id]);
    const key = noKeys ? '' : keyOf(id);
    let client = null;
    if (key && url) {
      const ck = id + '|' + url;
      if (!cache.has(ck)) cache.set(ck, createSmm(key, url));
      client = cache.get(ck);
    }
    return { id, label: (defs[id] && defs[id].label) || id, url, client, hasKey: !!key };
  });
  const byId = new Map(list.map((p) => [p.id, p]));
  return {
    ids, list, size: ids.length, defaultId: ids[0],
    get: (id) => byId.get(String(id)) || null,
    clientOf: (id) => (byId.get(String(id)) || {}).client || null,
  };
}
```

### 2-3. 마이그레이션 — 순서가 전부입니다

옛 주문은 **전부 smmkings·틱톡입니다. 지금은 100% 확실하게 그렇게 말할 수 있고, 패널이 섞인 뒤엔 영원히 말할 수 없습니다.** 그래서 backfill은 두 번째 패널 설정보다 **반드시 먼저** 돌려야 합니다.

현재 규모(확인함): `data/c/lun8/orders.json` 1건, `data/c/bayonn/orders.json` 15건. 시트 `_orders` 탭에 더 있는지는 **미확인**입니다.

## 8. 인스타 가드닝을 실제로 켜려면 더 필요한 것

**팔로워·링크가 어디서 오는지 확인한 결과 — 데이터는 이미 있습니다. 없는 건 '집행 경로'입니다.**

확인된 것:
- **인스타 핸들**: `appsscript/Code.gs:266-269, 281` (`igHandle`, `plat='tk'|'ig'|'both'`)과 `readPlat_`(141-155행)의 `a.ig.handle`. 정제는 `igHandleFrom_`(188행) — 릴스·게시물 링크를 계정으로 오인하지 않습니다.
- **인스타 팔로워**: `src/ig-sync.js`의 `runIgSync`가 스크랩해서 시트 `ig.followers`에 되씁니다(106행). 로컬 사본은 `data/c/lun8/ig-scan-latest.json`(**파일 실재 확인**). 화면은 시트 → `platBlock`의 `src.followers`(914행) → `d.ig.fol`로 이미 표시하고 있습니다.
- **패널 상품**: 최신 카탈로그에 `instagram`+`follow` 서비스가 **38개** 있습니다(확인함). 예: `#7178 $1.05/1k · min 10 · refill true`, `#4973 $0.21/1k · refill false`.

**막고 있는 것 — 집행 경로가 인스타 팔로워를 못 봅니다.**
- `/api/plan`은 `scanLatest(campaign)`(649행) = `scan-latest.json` = **틱톡 스캔 결과**만 봅니다.
- `/api/execute`는 `scanAccounts(accounts)`(691행) = Playwright **틱톡 프로필** 스크래퍼만 부릅니다.

그래서 §5까지 다 해도 인스타 계획의 `a.current`가 항상 `null` → 전부 `errored`가 됩니다. 추가로 필요한 것:

1. **플랫폼별 '현재 팔로워' 공급자.** `scanAccounts`는 틱톡 전용입니다. 인스타는 `ig-scan-latest.json`을 읽되 **신선도 검사**가 필수입니다 — 낡은 팔로워로 사면 과충전(돈)이거나 과소충전(납품 미달)입니다.

   ```js
   //       server.js:660 이 이미 거절하는 것과 같은 종류의 위험이다.
   const IG_FRESH_MS = 24 * 3600 * 1000;
   ```
   신선하지 않으면 `errored`에 `'인스타 팔로워가 오래됐어요(N시간 전) — 인스타 스캔을 먼저 돌려주세요'`.
2. **비공개 계정 제외.** `ig-sync`는 `isPrivate`를 이미 받아옵니다(88행). 대부분의 패널이 비공개 계정에 팔로워를 못 넣습니다 → `errored`로 빼야 합니다. (패널이 실제로 거절하는지는 **미확인**)
3. **인스타 목표치.** `campaign.target/min`은 캠페인당 하나(1100/1000)이고 화면도 `GTARGET/GMIN` 하드코딩입니다(`lun8.html:1083`). 인스타도 1000 기준인지 — **미확인, 대표님 결정 사항.**
