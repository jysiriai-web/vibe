# M0 · 0_intake — 브랜드 소싱·입력

파이프라인 시작점. **"영업할 브랜드를 찾아 6월 시트에 넣는다"** (= 사용자가 직접 하던 부분의 자동화).

## 소스 2채널
1. **DB-마이닝** — 마스터(`브랜드 에셋` 3094행)·`네이버뷰티`에서 **아직 미발송 + 이메일 보유** 브랜드 추출.
   → 단, 2026-06 기준 마스터는 거의 소진(1887 발송이력). 신규 후보 극소수(7개).
2. **웹 소싱** — `source-new-brands` 워크플로우(8니치 병렬 검색)로 **신생 인디 브랜드** 발굴.
   → DB가 마른 지금의 주력. 2022년 이후 런칭·인플루언서 마케팅 수요 큰 곳 위주, 민감/대기업 제외.

## 흐름
```
[소싱 워크플로우]  니치 병렬 웹서치(Source) → skipList 중복제거 → 실존·인스타·ICP 재검색(Verify)
                    → candidates_*.csv (브랜드명·카테고리·인스타·근거)
[시트 투입]        run.py --file → [중복제거: 대상탭·브랜드에셋·_보류·기존DB] → 6월 append
                                                                       (발송적합도 빈칸 → M1 차례)
```
- **Source**: 프로필 니치별 병렬 검색. **Verify**: 찾은 걸 배치로 다시 웹검색해 *실재하나 / 인스타 맞나 / ICP 맞나* 확인하고 못 믿으면 drop → 환각·동명혼동 제거(정확도 게이트).
- **비대칭 세팅(정확도↑·낭비↓)**: 오케스트레이터는 max, 워커(finder·verify)는 **Sonnet·medium**. max effort를 워커에 주면 검색 대신 추측이 늘어 환각↑·토큰낭비. 프로필 `workerModel:"opus"`로 최고품질 소싱도 가능.

## 사용법
```bash
# 소싱 결과 CSV를 6월에 투입 (배치 30개씩 권장)
python run.py --file candidates_0613.csv --limit 30          # dry-run
python run.py --file candidates_0613.csv --limit 30 --apply  # 실제 추가
python run.py 조선미녀 새브랜드 --apply                        # 브랜드명 직접
```
- CSV 헤더: `브랜드명, 카테고리, 인스타, 근거, …` (컬럼명으로 인식, 순서 무관)
- `--limit N`: 이번 배치 N개만, 나머지는 CSV에 남겨 다음 배치용
- 기본 **dry-run**, `--apply` 시 백업 후 추가
- `--tab 인터참`: 6월 말고 다른 탭에 투입(이벤트 트랙 등). 대상 탭 + 마스터·_보류·기존DB·6월과 중복 대조.

## 모듈형·재사용 (프로필)
"무엇을 찾을지"는 **`profiles/*.json` 1장**으로 분리됨. 같은 엔진에 프로필만 갈아끼우면 다른 타깃/시트로 재사용.
- 소싱 엔진(범용) = `source_brands.workflow.js` (Source→중복제거→Verify). 프로필을 `args`로 받음.
- 프로필 예: `profiles/siriai_kbeauty.json`(일반 아웃바운드)·`profiles/intercharm.json`(이벤트 트랙).
- 자세한 사용법·필드 = `profiles/README.md`. 다른 사람도 자기 프로필+자기 시트로 그대로 씀.

## ⚠️ 토큰·중단 규칙 (소싱·이메일 등 토큰 헤비 작업 — 필독, 사용자 명시)
1. **토큰 다 쓰면 거기서 STOP.** 소싱·이메일검색은 복잡하진 않지만 토큰을 많이 쓴다. 한도에 닿으면 **작업 중지가 기본 전제**.
2. **리셋돼도 자동 재개 금지.** 토큰이 다시 차도, 사용자가 후속 지시로 "재개하라"고 **명시하지 않았으면 더 진행 X**. (과거 실수: 한도 후 멋대로 재실행 → 토큰만 낭비.)
3. **예외 = 소액 회수만.** 진행 중 한도에 걸려 작업물이 0이 될 상황 + "조금만 더 쓰면 건질 수 있다"면 → 약간은 써서 **건진다**. (전체 재실행 ✗ / 작업물 회수 ○.)

## 체크포인트 청크 소싱 (중단해도 손실 최소화)
저장 단위는 **청크 경계**다 — 워크플로우는 실행 중 디스크에 못 쓰므로, 청크가 끝나 결과가 반환돼야 `append`된다. 따라서:
- ✅ **완료된 청크**는 CSV에 저장 → 안 날아감.
- ❌ **청크 도중 한도로 죽으면 그 청크는 통째로 0** (반환 전이라 저장 불가). ← 실제 발생함(과장 금지: "절대 안 날아감"이 아니라 "완료분만 보존").

**그래서 손실 최소화 = 작게·빨리:**
- **청크를 작게** (권장 2~3 니치/회). 죽어도 잃는 게 작고, 빨리 끝나 한도 전 반환 확률↑.
- **finder 검색 캡**(프로필 `searchCap`, 기본 12회). 과검색(실측 40~70회!)하다 **반환 직전** 죽는 게 0의 주범 → "적게라도 반드시 반환"이 1순위.
- 청크 끝날 때마다 `checkpoint.py append` 즉시.
```bash
# 1) base 프로필 + 기존 CSV → working 프로필(skipList 누적)
python checkpoint.py init --base profiles/siriai_kbeauty.json --csv 신규브랜드_서치리스트.csv --perNiche "5~9"
#    → profiles/_working.json 을 Read 해서 Workflow args 로 넘긴다 (★니치 2~3개씩만)
# 2) 워크플로우 결과를 _chunk_result.json 으로 저장 후:
python checkpoint.py append --result _chunk_result.json --csv 신규브랜드_서치리스트.csv --working profiles/_working.json
#    → CSV 누적 + working.skipList 갱신(다음 청크가 안 겹침). 반복.
```
- 누적 산출물 = running CSV, 불어나는 제외목록 = `profiles/_working.json`(재생성물 → `_*` 스크래치).
- 한도로 죽은 청크라도 검색 흔적·도출 브랜드는 **트랜스크립트**에 남음(`subagents/workflows/<runId>/agent-*.jsonl`) → 소액 회수 가능(규칙 3).

## 데이터 계약
- **입력**: candidates CSV (브랜드명·카테고리·인스타·근거)
- **출력(6월 신규행)**: `브랜드명` · `구분`(카테고리) · `인스타`(클릭링크) · 나머지 빈칸
  - `발송적합도`는 **빈칸** → 발송큐에 안 섞임(이중발송 방지). 다음 단계 **M1(1_collector)**이 이메일·적합도를 채움.
- 코드 의존 0. 다음 모듈은 6월 `발송적합도` 열로만 연결.

## 안전장치
- 백업 → dry-run → `--apply` (모든 쓰기)
- **4개 탭**(6월·브랜드에셋·_보류·기존DB)과 중복·이력 대조 (재발송 방지)
- 민감 카테고리(생리대·여성청결·전문의약품·다이어트) 자동 `메일주의` 태깅
- 정규화(`norm`)로 회사 접미사·공백·기호 무시한 동일 브랜드 판별
