# 4_track — 추적(열람·클릭·회신 감지) (⬜ 설계)

## 1. 목적

3_send가 발송 완료한 메일(발송단계=발송)을 대상으로, Gmail API로 답장 스레드를 폴링하여 회신 여부를 감지하고, Mailsuite CSV 또는 자체 추적링크 결과를 보조 인풋으로 받아 열람·클릭 정보를 6월 탭에 기록한다. 이 모듈은 읽기 위주로 동작하며, 시트 쓰기는 백업 후 dry-run→--apply 절차를 따른다. 다운스트림 모듈(5_reply 등)은 이 모듈이 갱신한 열 상태만 보고 동작한다.

---

## 2. 데이터 계약

### 입력

| 소스 | 열 / 필드 | 조건(읽기 필터) |
|---|---|---|
| 6월 탭 | 발송단계 | == `발송` |
| 6월 탭 | Gmail_스레드ID | 비어있지 않음 (3_send가 기록) |
| 6월 탭 | 수신거부 | 비어있거나 `N` (값=`Y`면 스킵) |
| Gmail API | 스레드 내 메시지 목록 | 발송자≠본인인 메시지 존재 여부 |
| Mailsuite CSV (선택) | 메일주소, 열람여부, 클릭여부, 열람일시 | 수동 업로드 or 예약 추출 |
| 자체 추적링크 로그 (선택) | 메일주소, 클릭일시 | 추적서버 로그 or Sheets 웹훅 |

### 출력

| 열 | 쓰기 내용 | 조건 |
|---|---|---|
| 열람 | `Y` | Mailsuite/추적링크에서 확인된 경우만 |
| 클릭 | `Y` | 동상 |
| 회신 | `Y` | Gmail 스레드에 답장 메시지 존재 |
| 회신일자 | 첫 답장 수신 일시 (YYYY-MM-DD HH:MM) | 회신=Y 확정 시 |
| 발송단계 | `회신` | 회신=Y이고 현재 발송단계=`발송` 또는 `열람`·`클릭` |
| 발송단계 | `열람` 또는 `클릭` | 회신 없고 열람/클릭만 감지된 경우, 현재=`발송`일 때만 |
| track_갱신일시 | 마지막 폴링 일시 | 매 실행마다 갱신 (감사로그용) |

> 멱등 원칙: 이미 `회신` 이상인 행(관심·리드·수신거부·종료 등)은 이 모듈이 건드리지 않는다. 자기 입력상태(`발송`·`열람`·`클릭`)만 보고 출력상태로 전이.

## 3. 메커니즘

### 3-1. 회신 감지 (Gmail API — 신뢰도 높음)

1. 6월 탭에서 발송단계 IN (`발송`, `열람`, `클릭`) 행을 전부 읽는다.
2. 각 행의 `Gmail_스레드ID`로 `gmail.users.threads.get(userId='me', id=thread_id)` 호출.
3. 스레드 내 메시지 중 `From` 헤더가 발신자(서비스계정 또는 OAuth 계정) 이메일이 아닌 메시지가 존재하면 → 회신 확정.
4. 첫 답장 메시지의 `internalDate`를 회신일자로 기록.
5. 회신 없으면 열람·클릭만 갱신하거나 현상 유지.

**인증**: Gmail은 OAuth 2.0 refresh-token 방식. `token.json` 파일로 자동 갱신. 스코프는 `gmail.readonly`(읽기 전용) — 메일 발송·삭제 권한 없음.

### 3-2. 열람·클릭 감지 (보조 — 신뢰도 낮음)

**A. Mailsuite CSV 경로**
- Mailsuite 대시보드에서 월별 추적 데이터 CSV 수동 다운로드 → `4_track/input/mailsuite_YYYYMMDD.csv` 배치.
- 스크립트가 `input/` 디렉터리에서 가장 최근 파일 자동 선택.
- 수신자 이메일 기준으로 6월 탭과 매칭 → 열람/클릭 갱신.

**B. 자체 추적링크 경로 (선택 구현)**
- 3_send 단계에서 본문 URL에 `?ref=<행ID 해시>` 파라미터 삽입.
- 클릭 로그를 Google Sheets 웹훅 or 경량 서버(Python/Flask)로 수집.
- `4_track/input/click_log.csv` 또는 별도 탭에서 읽어 매칭.
- 현재 미구현, 3_send 발송 실적 쌓인 후 도입 여부 결정.

### 3-3. 시트 매칭 키

- 기본 매칭: `이메일주소` 열 (유일키). 중복 이메일 행이 있을 경우 `Gmail_스레드ID`로 2차 확인.
- Mailsuite CSV의 이메일이 6월 탭에 없으면 `unmatched_log.csv`에 기록하고 패스 — 자동 신규 행 생성 금지.

### 3-4. LLM 사용 없음

이 모듈은 규칙 기반 매칭 + API 폴링으로만 동작한다. 회신 본문 분석(관심 여부 분류 등)은 5_reply 모듈 소관.

## 4. 상태 전이

```
[발송]
  ├─ 회신 감지됨          → [회신]  (회신일자 기록)
  ├─ 열람만 감지됨        → [열람]
  └─ 클릭만 감지됨        → [클릭]

[열람]
  ├─ 회신 감지됨          → [회신]
  └─ 클릭 추가 감지됨     → [클릭]

[클릭]
  └─ 회신 감지됨          → [회신]

[회신] 이상 단계           → 이 모듈 개입 없음 (5_reply 이후 소관)
[수신거부=Y]               → 이 모듈 스킵
[종료·제외]                → 이 모듈 스킵
```

> 열람·클릭 신뢰도가 낮으므로 `[열람]` → `[클릭]` 역전이는 허용하지 않는다(클릭이 열람보다 하위 단계가 아니라 별개 신호이기 때문). 두 신호가 모두 있으면 `[클릭]`으로 기록.

## 5. 안전·주의

### 5-1. 되돌리기

- 시트 쓰기 전 반드시 6월 탭 대상 행 스냅샷을 `4_track/backup/backup_YYYYMMDD_HHMMSS.csv`로 저장.
- `--dry-run` 플래그: 실제 시트에 쓰지 않고 변경 예정 diff를 콘솔 출력. 기본값 dry-run.
- `--apply` 플래그 명시해야 실제 쓰기 실행.
- 롤백 필요 시: `restore.py --backup backup_YYYYMMDD_HHMMSS.csv` 로 대상 열만 덮어쓰기.

### 5-2. 이중처리 방지

- 회신 열이 이미 `Y`인 행은 재처리 시 덮어쓰지 않는다.
- `track_갱신일시` 열로 마지막 실행 기록 — 같은 실행 세션에서 동일 행 두 번 쓰기 방지.
- Gmail API 호출 시 스레드 캐시 파일(`4_track/cache/thread_cache.json`)에 결과 저장, TTL 30분. 재실행 시 캐시 히트면 API 재호출 생략.

### 5-3. 사람 승인 게이트

- 이 모듈의 핵심 동작(읽기 + 시트 갱신)은 되돌릴 수 있으므로 자동 실행 허용.
- 단, 발송단계를 `회신` 이상(관심·리드 등)으로 올리는 것은 이 모듈 범위 밖. 5_reply에서 사람이 확인 후 수동 갱신 또는 별도 승인 게이트.
- `--apply` 실행 후 변경된 행 수가 예상치(전체 발송 행의 30% 초과 등 이상치)이면 경고 출력 후 중단. 임계값은 `config.yaml`에서 조정.

### 5-4. 메일주의 (민감 제품군 경고)

- 6월 탭에 `메일주의` 열이 `Y`인 행은 폴링 대상에 포함하되, 로그에 `[주의]` 태그를 붙여 별도 표시.
- 회신 감지 시 콘솔에 경고 메시지 출력: "메일주의 행 회신 감지 — 5_reply 처리 시 별도 확인 필요".
- 자동으로 발송단계를 바꾸는 행동은 동일하게 허용하되, 5_reply 담당자가 인지하도록 로그 기록.

### 5-5. OAuth 토큰 관리

- `token.json`은 `.gitignore`에 포함, 절대 커밋 금지.
- refresh-token 만료 시(보통 7일 미사용 or 구글 정책 변경) 스크립트가 오류 메시지와 재인증 URL 출력 후 종료. 자동 브라우저 열기는 서버 환경 고려해 기본 비활성.
- 서비스계정(시트용)과 OAuth(Gmail용) 인증 파일 경로는 `config.yaml`에서 분리 관리.

## 6. 구현 메모

### 6-1. 예상 파일 구조

```
4_track/
  run.py                  # 진입점. --dry-run / --apply / --restore 플래그
  tracker.py              # 핵심 로직: Gmail 폴링, CSV 매칭, 상태 갱신
  gmail_client.py         # Gmail API 래퍼 (OAuth refresh 포함)
  sheet_client.py         # gspread 래퍼 (../_shared/ 재사용 or 얇은 래퍼)
  config.yaml             # 탭명, 열명, 임계값, 파일경로 등 모든 하드코딩 분리
  restore.py              # 백업 CSV로 시트 롤백
  input/
    mailsuite_YYYYMMDD.csv  # 수동 배치용
    click_log.csv           # 자체 추적링크 로그 (선택)
  backup/
    backup_YYYYMMDD_HHMMSS.csv
  cache/
    thread_cache.json       # Gmail API 응답 캐시 (TTL 30분)
  logs/
    track_YYYYMMDD.log
    unmatched_log.csv       # Mailsuite 매칭 실패 이메일
```

### 6-2. 의존

| 패키지 | 용도 |
|---|---|
| `gspread` + `google-auth` | 시트 읽기/쓰기 (`../_shared/` 재사용) |
| `google-api-python-client` | Gmail API |
| `google-auth-oauthlib` | OAuth 2.0 flow |
| `pandas` | CSV 매칭·diff 처리 |
| `pyyaml` | config.yaml 파싱 |

 Python 버전: 3.10+. `requirements.txt`는 `4_track/` 로컬 또는 `_shared/`에서 공유.

### 6-3. 실행 예시

```
# 미리보기 (기본)
python 4_track/run.py --dry-run

# 실제 갱신
python 4_track/run.py --apply

# 롤백
python 4_track/restore.py --backup 4_track/backup/backup_20260612_140000.csv
```

### 6-4. 미정 / 결정 필요 항목

| 항목 | 현황 | 결정 필요 사항 |
|---|---|---|
| Mailsuite 추출 주기 | 수동 배치 | 자동 추출 API 존재 여부 확인 필요 |
| 자체 추적링크 서버 | 미구현 | 도입 여부 — 3_send 발송 실적 100건 이상 쌓인 후 결정 권장 |
| Gmail API 폴링 주기 | 미정 | 수동 실행 vs. cron(1회/일) — 발송 볼륨에 따라 결정 |
| `Gmail_스레드ID` 열명 | 3_send 설계에 의존 | 3_send와 열명 반드시 일치 확인 |
| OAuth 계정 | 미정 | 발송 계정과 동일 계정 사용 여부 (발송과 추적 계정 분리 시 스레드 매칭 로직 변경 필요) |
| 이상치 임계값 (30%) | 임시 | 최초 실 데이터 기반으로 조정 |

> 이 모듈은 데이터가 쌓이기 전까지는 설계·config 확정 단계. 3_send 가동 후 발송 행이 생기면 Gmail 폴링부터 구현하고, Mailsuite/추적링크는 이후 단계에서 붙인다.
