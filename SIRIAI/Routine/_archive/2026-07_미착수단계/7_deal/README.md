# 7_deal — 미팅·계약 성사 (⬜ 설계)

## 1. 목적

`5_reply` 또는 `8_followup`에서 `발송단계=미팅` 또는 `발송단계=계약`으로 갱신된 행을 대상으로, 미팅 일정 추적·계약 진행 상태 갱신·성사 기록을 담당한다. 실제 미팅 진행과 계약 협상은 전적으로 사람이 하며, 이 모듈은 일정 리마인더·자료 링크 관리·상태 전이·성사 브랜드 제외 명단 반영만 수행한다. 출력은 6월 탭의 `미팅`, `성사여부`, `발송단계` 열 갱신 및 `_shared/exclude_next_month.csv` 추가다.

---

## 2. 데이터 계약

### 입력

| 출처 | 열 이름 | 조건 / 기대값 |
|------|---------|---------------|
| 6월 탭 | 발송단계 | `미팅` 또는 `계약` |
| 6월 탭 | 회신일자 | 비어 있지 않음 (upstream 보장) |
| 6월 탭 | 메일주의 | `Y` 여부 확인 (민감 제품군 경고) |
| 6월 탭 | 미팅 | 빈 값 또는 기존 날짜 문자열 (`YYYY-MM-DD`) |
| 6월 탭 | 성사여부 | 빈 값 (입력 시점 기준) |
| `_shared/exclude_next_month.csv` | 브랜드명, 월 | 누적 제외 명단 (읽기) |

### 출력

| 열 이름 | 갱신 내용 |
|---------|-----------|
| 미팅 | 미팅 예정일 또는 완료일 기록 (`YYYY-MM-DD`) |
| 발송단계 | `미팅` → `계약` → `성사` 또는 `거절` → `종료` |
| 성사여부 | `Y` (성사) 또는 `N` (거절·종료) |
| `_shared/exclude_next_month.csv` | 성사 브랜드 행 추가 (재발송 제외) |

> 이 모듈은 `발송`, `열람`, `클릭`, `회신`, `발송일자`, `회신일자` 열을 **읽지 않고 쓰지 않는다.** 연결은 `발송단계` 열 하나로만 한다.

## 3. 메커니즘

### 3-1. 대상 행 필터링

`gspread`로 6월 탭 전체를 읽은 뒤, `발송단계 in ['미팅', '계약']`인 행만 추린다. 이미 `발송단계=성사` 또는 `종료`인 행은 건너뛴다(멱등 보장).

### 3-2. 미팅 일정 기록

- 사람이 직접 `미팅` 열에 날짜를 입력하는 것이 1차 방법이다.
- 자동화 옵션: Google Calendar API 연동(미정, §6 참조). 연동 시 서비스계정이 아닌 OAuth 계정으로 캘린더를 조회해 해당 브랜드명이 포함된 이벤트를 찾아 날짜를 채울 수 있다. 현재는 구현하지 않는다.
- `--remind` 플래그 실행 시: 미팅 예정일이 오늘 기준 D-1, D-0인 행을 stdout으로 출력(또는 Gmail Draft 생성). 발송하지 않는다.

### 3-3. 상태 전이 적용 (`--apply`)

사람이 시트에서 다음 중 하나를 수동 입력한 열을 읽어 상태를 전이한다:

| 사람이 입력하는 트리거 열 | 모듈 동작 |
|--------------------------|----------|
| `미팅` 열에 날짜 기입 + `발송단계=미팅` | `발송단계` → `계약` 으로 갱신 |
| `성사여부=Y` 수동 입력 + `발송단계=계약` | `발송단계` → `성사` 로 갱신, 제외 명단 추가 |
| `성사여부=N` 수동 입력 + `발송단계=계약` | `발송단계` → `거절` → `종료` 로 갱신 |

> 모듈이 먼저 쓰는 것이 아니라, 사람이 트리거 열을 채우면 모듈이 `발송단계`와 `성사여부`를 맞춰 쓰는 구조다.

### 3-4. 성사 브랜드 제외 명단

`성사여부=Y`가 확인된 브랜드는 `_shared/exclude_next_month.csv`에 `브랜드명, 계약월(YYYY-MM)` 형식으로 추가한다. `1_collect` 및 `2_compose`는 이 파일을 읽어 다음 달 재발송을 막는다(별도 코드 의존 없음, 파일로만 연결).

### 3-5. LLM 사용

이 모듈은 LLM을 사용하지 않는다. 상태 전이 로직은 규칙 기반이며, 계약 내용 해석·협상 제안은 사람 소관이다.

---

## 4. 상태 전이

```
[미팅]
  └─ 미팅 열 날짜 기입 (사람) + --apply
       → [계약]
            ├─ 성사여부=Y (사람) + --apply
            │    → [성사]  →  exclude_next_month 추가
            └─ 성사여부=N (사람) + --apply
                 → [거절] → [종료]
```

- `수신거부` 상태 행이 이 모듈에 도달한 경우: 건너뛰고 경고 로그만 남긴다 (upstream 오류 신호).
- `발송단계` 이외 열(발송·열람·클릭 등)은 이 모듈이 변경하지 않는다.

---

## 5. 안전·주의

### 되돌리기

- 모든 시트 쓰기 전 해당 행 스냅샷을 `7_deal/logs/YYYYMMDD_backup.jsonl`에 저장한다.
- `--dry-run` 기본 동작: 변경 예정 내용을 stdout 표로 출력하고 시트에 쓰지 않는다.
- `--apply` 플래그를 명시해야만 실제 쓰기가 실행된다.
- 롤백 필요 시 `backup.jsonl`을 읽어 원래 값으로 덮어쓰는 `--rollback YYYYMMDD` 옵션을 제공한다.

### 이중처리 방지

- `발송단계=성사` 또는 `종료`인 행은 재처리하지 않는다(멱등).
- `exclude_next_month.csv` 추가 시 중복 브랜드+월 조합은 건너뛴다(누적식).

### 사람 승인 게이트

- `성사여부` 열은 모듈이 자동으로 쓰지 않는다. 사람이 먼저 시트에 Y/N을 기입해야 모듈이 `발송단계`를 뒤따라 갱신한다.
- `발송단계=계약` → `성사` 전이는 되돌릴 수 없는 상태 변경이므로, `--apply` 실행 전 stdout에 대상 행 목록과 `[Y/n]` 확인 프롬프트를 출력한다. `n` 입력 시 중단.

### 메일주의 (민감 제품군)

- `메일주의=Y` 행이 처리 대상에 포함되면 dry-run 및 --apply 실행 시 해당 행을 별도 섹션으로 강조 출력한다.
- 민감 제품군 브랜드의 계약 성사 기록은 정상 처리하되, 리마인더 메일 초안 생성 시 수신자·내용을 사람이 검토하도록 Draft 상태로만 생성한다(자동 발송 없음).

## 6. 구현 메모

### 예상 파일 구조

```
7_deal/
  run.py              # CLI 진입점 (--dry-run / --apply / --remind / --rollback)
  deal_tracker.py     # 상태 전이 로직, 시트 읽기/쓰기
  remind.py           # 미팅 D-1/D-0 리마인더 출력 또는 Gmail Draft 생성
  exclude_writer.py   # exclude_next_month.csv 추가
  logs/               # YYYYMMDD_backup.jsonl 저장
```

### 의존

- `../_shared/` : `sheet_client.py` (gspread 래퍼), `exclude_next_month.csv`
- 인증: 시트 조작 = 서비스계정 JSON, Gmail Draft = OAuth 2.0 (별도 token.json)
- 외부 라이브러리: `gspread`, `google-auth`, `google-api-python-client` (Gmail·Calendar)
- 타 모듈 코드 직접 import 없음

### 미정·결정 필요 항목

| 항목 | 현황 | 결정 필요 내용 |
|------|------|----------------|
| Google Calendar 연동 | 미구현, 설계 여지만 확보 | OAuth 계정 공유 여부, 이벤트 명명 규칙 |
| 리마인더 전송 방법 | stdout 출력 우선, Gmail Draft 옵션 | Draft 수신자(담당자 메일) 확정 |
| `exclude_next_month.csv` 포맷 | 브랜드명+계약월 2열 초안 | 브랜드명 표준화 기준 (시트 표기 vs 공식명) |
| `발송단계=계약` 수동 입력 규칙 | 사람이 직접 쓰는 전제 | 입력 담당자·시점 프로세스 문서화 필요 |
| 이 모듈 최초 가동 시점 | 3_send 안정화 후 | 6월 탭에 미팅 이상 데이터가 5건 이상 쌓인 시점 |

> 현재는 설계·데이터 계약 확정 단계. `3_send` 가동 후 실제 미팅 데이터가 누적되기 전까지 구현 착수는 보류한다.
