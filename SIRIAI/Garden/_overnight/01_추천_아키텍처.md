# 추천 아키텍처 — 관제탑 + 무인 워커(시트 신호버스)

> 5개 설계를 5기준(①사용자마찰 ②구축난이도 ③밴안전 ④견고함 ⑤템플릿 재사용성)으로 심사하고,
> 가장 좋은 조각들을 접목한 최종 추천안 + 단계별 구현계획.
> 코드베이스 실제 파일·함수·라인을 근거로 작성. 비전문가가 읽을 수 있게, 대신 "무슨 파일·무슨 새 컴포넌트"까지 구체적으로.

---

## 0. 요약 (3분 버전)

- **채택: 설계 5 ≒ 설계 1** (둘은 사실상 쌍둥이). "사람은 클라우드 화면 하나만 보고, 대표님 PC엔 화면 없는 무인 워커가 돌며, 둘 사이 신호는 **이미 있는 구글시트(Apps Script 브릿지)**를 통해 오간다."
- **핵심 접목 3가지**:
  1. **돈은 클라우드로 올리지 않는다** (설계 1의 Option A + 설계 5가 스스로 권한 대안). SMM 키는 대표님 PC에만 → 지금의 "URL 알아도 물리적으로 지출 불가" 삼중방어를 **한 줄도 안 바꾸고** 그대로 유지. 클라우드는 비번 게이트(UX)만, 워커가 실제 집행 직전 비번을 한 번 더 검증.
  2. **터널(설계 3) 불채택** — cloudflared 세팅·새 공격면·Vercel 함수 타임아웃을 피한다. 시트버스는 대표님 PC가 **바깥으로 폴링만** 하므로 공유기·방화벽 구멍이 아예 필요 없다.
  3. **무거운 트레이앱(설계 4의 Electron/Tauri) 불채택** — 코드서명·자동업데이트 과투자(절제 원칙 위배)를 피하고, **로그인 시 숨김 자동시작 + 클라우드 하트비트 배지**로 대체. (트레이 아이콘은 나중에 선택 옵션.)
- **밴 대응**: 저녁 예약 자동(무인) + 사람 감독 온디맨드 **둘 다** 지원(설계 2가 뺀 온디맨드를 되살림 — 사용자 요구사항). VPN 수동전환은 "막혔을 때만 쓰는 비상 해치"로 격하.
- **왜 이게 이김**: 새 인프라 0 · 인바운드 0 · 돈 물리안전 유지 · 캠페인-불문(LUN8을 config만 추가로 얹음). 잔여 대가는 "폴링 지연 수 초"와 "집행하려면 워커가 켜져 있어야 함"뿐인데, 워커는 늘 켜져 있으니 실질 제약이 아니다.

## 1. 5개 설계 심사 (스코어카드)

★ 많을수록 좋음. (①사용자마찰: 낮을수록 ★, ②구축난이도: 낮을수록 ★)

| 설계 | ①마찰↓ | ②난이도↓ | ③밴안전 | ④견고함 | ⑤템플릿 | 한 줄 평 |
|---|---|---|---|---|---|---|
| **1. 폴링 워커(시트버스)** | ★★★★★ | ★★★☆ | ★★★★★ | ★★★★☆ | ★★★★★ | 완성형. 단 '트레이 패키징'을 넣으면 난이도↑ |
| **2. 야간 예약 전용** | ★★★☆ | ★★★★ | ★★★☆ | ★★★ | ★★★ | 온디맨드를 뺀 게 치명(요구 위배)+돈 클라우드화 |
| **3. 숨은 터널(cloudflared)** | ★★★★★ | ★★★ | ★★★★ | ★★★ | ★★★★ | 실시간 제어는 최고, 새 공격면·타임아웃이 대가 |
| **4. 트레이앱(Electron)** | ★★★★ | ★★☆ | ★★★★ | ★★★ | ★★★★ | 껍데기 과투자·돈 클라우드화가 발목 |
| **5. 관제탑+무인워커** | ★★★★★ | ★★★★ | ★★★★★ | ★★★★ | ★★★★★ | 설계1과 쌍둥이·자동시작이 더 가벼움 ← **채택** |

**기준별 판단 근거 (코드 사실 반영)**

- **③밴안전이 사실상 동률인 이유**: 밴 회피 두뇌(실제 크롬 `headless:false`, 집 IP, 순차 `concurrency=1`+jitter 0.9~2.6초, 연속 3회 실패 감지 `BLOCK_STREAK=3`, "못 봤다≠안 올렸다")는 **다섯 설계가 전부 기존 `content-core.js`/`tiktok-videos.js`를 그대로 재사용**한다. 차이는 "무인 예약"을 얼마나 안전하게 두느냐인데, 저녁창+쿠키통과분만 자동+막히면 포기의 조합은 1·3·4·5가 동일. **설계 2만** 온디맨드를 없애 "낮에 급히 필요할 때 방법이 없음" + "무인 침묵실패"가 도드라진다.
- **②구축난이도 갈림**: 스캔·돈·판정 두뇌는 **다섯 설계 모두 재사용(새로 안 만듦)**. 난이도는 오직 "클라우드↔로컬 배선"과 "자동시작 포장"에서 갈린다.
  - 설계 3 = cloudflared 서비스 + 로그온세션 프로세스 + 프록시 계층(스트리밍을 폴링으로 우회 필수) → 새 인프라·공격면.
  - 설계 4 = Electron/Tauri 패키징·코드서명·자동업데이트 → 껍데기에 힘이 많이 감.
  - 설계 1/5 = **새 인프라 0**. 이미 있는 Apps Script 브릿지(`src/sheet.js`)에 '작업탭' 하나 얹고, `node src/server.js`를 '화면 없는 폴러'로 돌리는 접착코드가 대부분.
- **④견고함에서 1·5가 앞서는 이유**: 신호가 시트를 거치므로 클라우드가 집 PC로 **직접 들어올 필요가 없다**(집 PC는 지금 브릿지 호출과 똑같이 바깥으로 폴링만) → 공유기 포트포워딩·방화벽·터널 시크릿 유출 같은 실패원인이 원천 소거. 브릿지는 이미 구글 일시 오류(JSON 아닌 HTML)를 **3회 재시도로 흡수**하고(`sheet.js` `bridgeCall`), 쓰기가 전부 idempotent라 안전. 잔여 약점은 "폴링 지연"뿐 → 활성 세션엔 폴링을 2~3초로 조여 완화.
- **⑤템플릿에서 1·5가 만점인 이유**: 신호가 `campaign.id`별로 분리되므로 LUN8을 2번째로 얹고 3번째는 config 추가만으로 붙는다. 터널/트레이도 config로 확장되지만, "인바운드 없음 + 시트가 진실"이 캠페인이 늘어도 그림을 안 바꾼다.

**결론**: 설계 1과 5는 같은 가족. **설계 5의 가벼운 자동시작**(트레이 없이 로그인 자동실행)을 뼈대로, **설계 1의 두 강점**(ⓐ돈을 '또 하나의 워커 작업'으로 = 물리안전 유지, ⓑ클라우드 하트비트 배지로 온/오프라인 표시)을 접목한다. 실시간이 정말 필요해지면 그때 설계 3의 터널을 '버스 교체 옵션'으로 스왑(아래 §7 폐기지점).

## 2. 추천 아키텍처 그림 (글로 설명)

```
            ┌──────────────────────────────────────────────────────┐
   사람 →   │  클라우드 대시보드 1개 (Vercel URL · 북마크 · 비번없음)  │
            │  • 보기/검수/비고/예정일/모집확인/납품  = 시트에 직접 씀  │
            │  • [스캔]/[집행] 버튼 = '작업 요청'을 시트에 깃발로 꽂음   │
            │  • 상단 배지: 🟢 워커 온라인(8초 전) / 🔴 PC 꺼짐        │
            └───────────────┬──────────────────────────────────────┘
                            │ (모두 바깥으로 나가는 HTTPS = Apps Script 브릿지)
                            ▼
   ┌────────────────  구글 시트 = 유일한 진실 + 신호버스  ────────────────┐
   │  ■ 데이터 열: 계정·팔로워·콘텐츠(17)·검수(19·20·21)·성과(27~30)      │
   │  ■ '_worker' 탭(신규): 작업큐 · 진행상태 · 제어(go/resume/stop) · 하트비트 │
   └───────────────▲──────────────────────────────────────────────────┘
                   │ 5~10초 폴링(바깥으로만) — 인바운드 포트·공유기 설정 불필요
                   │
   ┌───────────────┴──────────────────────────────────────────────────┐
   │  대표님 PC = 화면 없는 무인 워커  (src/worker.js, 신규)              │
   │  • 로그인 시 자동시작(숨김, 검은 창 0개) · 크래시 시 자동재시작        │
   │  • 작업 발견 → 기존 '두뇌'를 그대로 호출 (한 줄도 안 고침):           │
   │       content-scan → runContentScan  (실제 크롬 창 + 집 IP + 사람 감독) │
   │       execute      → placeOrders     (로컬 .env SMM키, EXEC_PW 재검증) │
   │  • 결과는 지금과 똑같이 pushCellsToSheet 로 '같은 시트'에 되쓰기        │
   └──────────────────────────────────────────────────────────────────┘
```

**한 줄**: 클라우드=유일한 리모컨, 시트=유일한 진실 + 우체통, 대표님 PC 워커=집 IP·실제 크롬·SMM키가 필요한 '물리적 일'만 조용히 대행.

**왜 배관을 거의 새로 안 만드나 (핵심 우아함)**: 스캔 결과 '데이터'는 `runContentScan`이 **이미** 시트에 직접 쓴다(콘텐츠 17 / 음원 19 / 음원구간 20 / 해시태그 21 / 조회·좋아요·댓글·공유 27~30, `pushCellsToSheet`). 그래서 클라우드는 평소처럼 `/api/data`만 읽으면 최신치가 보인다. 새로 놓는 신호선은 오직 **(a) 작업 요청 (b) 진행상태 (c) 제어신호** 3가지뿐 — 실제 결과는 기존 경로가 나른다.

**돈 안전이 공짜로 유지되는 이유 (가장 중요)**: 워커는 `GARDEN_CLOUD`/`VERCEL` 환경변수 **없이** 도는 그냥 로컬 서버다 → `src/server.js:29`의 `const key = CLOUD ? null : process.env.SMMKINGS_API_KEY`에서 **CLOUD=false → 키 살아있음 → 집행 가능**. 반대로 Vercel 배포는 CLOUD=true라 여전히 `key=null`. 즉 **돈 방어코드를 하나도 안 건드리고** "클라우드엔 키가 물리적으로 없다"가 그대로 성립한다. 클라우드가 새로 하는 일은 '집행 요청을 시트에 적는 것'뿐(키 불필요)이고, 워커가 집행 직전 `EXEC_PW`(`pwMatch`, timingSafeEqual 상수시간 비교)를 한 번 더 확인한다.

## 3. 사용자 워크플로우 3장면

전제: **사람이 여는 창은 언제나 클라우드 URL 하나**(북마크). bat·터미널·localhost 탭 없음.

### 장면 1 — 평소 조회·검수 (PC 꺼져 있어도 됨)
1. 북마크한 클라우드 주소를 폰/노트북 어디서든 연다.
2. 상단바 배지로 워커 상태 확인: 🟢 온라인 / 🔴 PC 꺼짐 — "스캔이 왜 안 도나?"를 헷갈릴 일이 없다.
3. 모집/업로드/가드닝/납품/정산 5탭은 지금처럼 시트에서 읽어 표시.
4. 검수(음원 19·음원구간 20·해시태그 21 준수/미준수 토글)·비고·링크·예정일·모집확인 = 셀 클릭 → 인라인 편집 → 저장. **이 경로(`/api/cell`)는 이미 클라우드에서 시트에 바로 쓴다**(LOCAL_ONLY 아님). 저장하면 그 셀은 '수동 잠금'돼서 다음 스캔이 안 덮음(수동 우선).
5. '납품시트 기입'도 여기서 누른다(장면=돈 아님, §5에서 클라우드화).
→ **창 하나, 시트 하나. 편집은 한 군데서 한 번.**

### 장면 2 — 스캔 (업로드/조회수/개별)
1. 업로드 탭에서 [업로드 스캔] 클릭 → 클라우드가 시트 '_worker' 탭에 작업행 1개 append(type=content-scan, mode) → "스캔 요청됨 — PC 워커가 곧 시작합니다" 배지.
2. 대표님 PC 워커가 폴링 중 발견 → claim → 기존 `runContentScan` 호출. **대표님 화면에 실제 크롬 창이 뜬다**(봇 우회).
3. 쿠키 살아있으면(`data/tiktok-session.json`) 자동 진행. 로봇 인증이 필요하면 워커가 상태를 'awaiting-human'으로 바꾸고 → 클라우드에 "크롬 창에서 인증 통과 후 [스캔 시작] 누르세요". 대표님이 크롬에서 통과하고 클라우드에서 [스캔 시작] 클릭 → 워커가 제어칸 'go'를 읽어 진행(=지금 `/api/content-scan/confirm`이 `scanConfirmResolve`로 하던 일).
4. 진행 중: "32/120 계정 · 신규 8건" 실시간 표시(워커가 진행률을 상태칸에 미러).
5. 끝나면 요약 토스트 + 자동 새로고침. 결과는 워커가 시트에 되썼으니 그대로 보인다.
→ 사람이 본 건 클라우드 화면(+ 인증 순간 크롬 창 힐끗). bat·localhost 없음.

### 장면 3 — 돈 집행 (내부 팀, 비번 게이트, 물리안전 유지)
1. 가드닝 탭 → needs 하위탭(1,000 미만 계정) 체크 → [집행] 클릭.
2. 클라우드가 플랜 미리보기(수량·비용·잔액) 표시 → "집행 비밀번호" 모달 → 입력 → 확인.
3. 클라우드는 **키가 없으므로 직접 집행 못 한다** → 대신 시트에 execute 작업행을 append(대상·수량 + 비번검증 플래그).
4. 워커가 claim → 로컬 `.env`의 SMM 키로 기존 `placeOrders` 경로 실행. **집행 직전 `EXEC_PW`를 상수시간 비교로 2차 재검증**(클라우드 게이트가 뚫려도 워커가 막음), 잔액 부족이면 거부, 과금 직후 즉시 기록(기록 실패=배치 중단, "기록 없는 과금" 방지), 주문 멱등키로 이중과금 차단.
5. 주문번호·상태가 시트로 반영 → 클라우드 자동 갱신.
→ 클릭 흐름: 가드닝→체크→집행→비번→확인. **여전히 창 하나.** 단 이때는 워커가 켜져 있어야 함(늘 켜져 있음).

## 4. 스캔 처리 (저녁 예약 + 온디맨드)

밴 회피의 1차 수단은 **저녁창 + 순차처리 + jitter + 탭 최소화**(전부 기존 로직). VPN 수동전환은 "막혔을 때만 쓰는 비상 해치"로 격하 — 자동화의 기본 전제로 두지 않는다.

### (A) 저녁 예약 — 무인, 클릭 0
- **트리거**: 워커 안의 내장 시계(`setInterval` + '지금이 저녁창인가' 체크 — 무의존, 코드베이스 스타일과 일치)가 저녁(예: 19:30 / 21:30)에 스스로 발화. **Vercel Cron에 의존하지 않음** → 클라우드 설정 없이도 성립(원하면 나중에 예약시각을 시트 설정탭에서 편집 가능하게).
- **안전한 무인**: '쿠키로 통과되는 것만' 자동. 프로필이 저절로 렌더되면 진행, **로봇 인증이 뜨면(사람 없음) 짧게 기다렸다가 이번 창을 포기**하고 상태칸에 'deferred/세션 데우기 필요' 기록 → 크롬을 밤새 걸어두지 않는다. **CAPTCHA는 절대 자동으로 풀지 않는다**(사람만).
- **재시도 = 스케줄 구조로**: 업로드 스캔은 '미업로드 계정만' 대상이라, 이번 창에 못 한 계정은 **다음 저녁창에서 자연히 다시 대상**이 된다. 창 사이 2시간이 곧 IP 쿨다운.
- **침묵 실패 방지(필수)**: 쿠키 만료로 며칠 조용히 멈추는 걸 막기 위해, 상태칸 'authNeeded'를 클라우드 상단 **"세션 데우기 필요" 경고 배지**로 반드시 노출. 사람이 크롬 한 번 통과해 쿠키를 갱신하면 이후 며칠 다시 무인.

### (B) 온디맨드 — 사람 감독 (설계 2가 뺀 것을 되살림)
- 대표님이 PC 근처일 때 클라우드 버튼으로 full/perf(조회수)/개별/판정 실행. 로봇 인증은 사람이 크롬 창에서 물리적으로 통과(human-in-the-loop). **버튼(스캔 시작/재개/중지)은 전부 클라우드에** 있어 두 창을 juggle하지 않는다.
- **감독 게이트를 반드시 클라우드로 노출**(설계 5 위험 #6): `confirm`(인증 후 시작)·`blocked`(연속 3회 실패 → 재개/중지) 프롬프트를 로컬 화면이 아니라 클라우드 화면에 띄운다. 안 그러면 "한 화면" 약속이 깨진다.

### 상태전달 = 유일한 새 접착부
지금 서버 안에서 메모리로 도는 상태기계(`contentScanState`, `scanConfirmResolve`=인증 게이트, `scanResumeResolve`=차단시 재개 게이트, `src/server.js:37·41·42·309~368)를 **'시트 셀'로 미러링**만 바꾼다:
- `onWarmup` → 상태칸 = awaiting-human
- `waitForGo` → 워커가 제어칸이 'go'될 때까지 폴링(15분 타임아웃 유지)
- `onProgress` → 진행칸에 done/total 미러(스로틀: 몇 계정마다 — 기존 30초 SMM 스로틀과 같은 결)
- `onBlocked` → 상태칸=blocked + 이유. 제어칸 resume/stop 대기
- `shouldPause` → 제어칸이 pause/stop인지 검사
- **적응형 폴링**: 유휴 10초, 작업이 awaiting-human/blocked/scanning일 땐 2~3초로 당겨 클릭 지연 최소화.

## 5. 돈·납품·설정 클라우드화

| 대상 | 지금 | 추천 처리 | 이유 |
|---|---|---|---|
| **납품** `/api/deliver` | 클라우드 501 | **LOCAL_ONLY에서 제거** → 클라우드가 브릿지로 직접 시트→시트 복사 | 돈·집IP·크롬 다 불필요한 순수 시트작업. 로컬일 이유가 없음 |
| **조회·검수·비고·링크·예정일·모집확인** `/api/cell` | 이미 클라우드 됨 | 그대로 | LOCAL_ONLY 아님. 저장 시 수동잠금까지 이미 동작 |
| **돈**(집행/플랜/종료/포기/리필) | 클라우드 501 + 키 없음 | **'작업'으로 우회** — 클라우드 비번게이트 → 시트 작업행 → **워커가 로컬 키로 집행** | SMM 키를 Vercel에 안 올림 → "클라우드에서 지출 물리적 불가"라는 삼중방어 유지 |
| **설정**(환율 `/api/rate`·서비스 `/api/service`) | 로컬 파일 `campaigns.json`에만 씀(클라우드는 `writeCfg` throw) | 자주 바뀌는 **환율·서비스ID는 set-rate/set-service '작업'**으로 워커가 로컬 파일에 쓰거나 시트 설정탭으로 이관. 드물게 바뀌는 구조설정(해시태그·soundId)은 개발자 작업으로 문서화 | 이중 소스(campaigns.json vs Vercel env `CAMPAIGNS_JSON`)를 줄이되 무리해서 다 옮기지 않음(절제) |

**돈 클라우드화의 트레이드오프(명시 요청)** — 두 갈래:
- **A(채택): 워커가 집행.** 키를 대표님 PC에만 → 삼중방어(`CLOUD?null:key` + 라우트게이트 + 파일시스템) 유지. 대신 집행 시 워커(=PC)가 켜져 있어야 함. **가드닝 집행은 스캔 직후에 하므로 어차피 PC-온 세션**이라 자연스럽다.
- **B(불채택): Vercel이 SMM키로 직접 집행.** PC 꺼져도 됨·즉시성↑. 그러나 "돈은 클라우드에서 물리적으로 불가능"이 "비번만 알면 어디서든 가능"으로 약해진다. 팀 URL이 비번 없이 열리므로 집행 비번이 **유일한** 장벽이 되고, 비번 유출/피싱=실제 금전 손실. → **B는 권장 안 함.** (택한다면 강한 비번 + Vercel IP 허용목록 + 집행 1회당 상한 + 시도 rate-limit + 전수 로깅이 필수.)

## 6. 단계별 구현계획 (1·2·3)

스캔·돈·판정 '두뇌'는 **전부 재사용**(`runContentScan`/`scanOneProfile`/`judgeOneLink`/`runSync`/`placeOrders`/`buildPlan`, 그리고 브릿지 `sheet.js`). 새로 만드는 것은 대부분 **접착부(글루)**다. 각 단계 끝엔 '무엇이 손에 잡히나(사용자 체감)'를 적었다.

> 순서 원칙: **돈은 가장 마지막·가장 신중하게.** 1~2단계 동안 돈은 지금처럼 로컬 대시보드로 계속 집행(임시 병존)하고, 3단계에서 워커로 옮긴 뒤에야 로컬 대시보드를 은퇴시킨다.

### 단계 1 — 뼈대: 온디맨드 스캔을 시트버스로 (여기서 두 창·bat이 사라짐)
**새 컴포넌트**
- `appsscript/Code.gs` 확장: **'_worker' 작업탭** 핸들러. `doGet(action=worker-poll)` = 다음 queued 작업 반환, `doPost({job})` = 작업 append, `doPost({jobStatus})`/`{control}`/`{heartbeat})` = 상태·제어·하트비트 셀 update. (이미 헤더기반 read/write·cells 쓰기를 하므로 job CRUD 추가는 중간 규모. 데이터 열과 물리적으로 분리 배치해 경합 방지.)
- `src/worker-bus.js` (신규, 얇게): `readJob()`/`claimJob()`/`updateStatus()`/`readControl()`/`heartbeat()` — **버스 추상화를 얇게** 만들어 나중에 Vercel KV 등으로 스왑 가능하게.
- `src/worker.js` (신규, 핵심): 폴러 루프 → queued 발견 시 claim(원자적 status 플립 + 워커 단일인스턴스 락으로 중복실행 차단) → type에 맞는 기존 함수 호출 → 콜백↔시트 어댑터(§4) → 하트비트. `node src/worker.js`로 뜨고 **브라우저 탭은 안 연다**.
- `src/server.js` 핸들러에 클라우드 라우트 3개(모두 **LOCAL_ONLY 아님**): `/api/scan-request`(큐잉)·`/api/scan-status`(상태칸 읽기)·`/api/scan-control`(go/resume/stop 쓰기).
- `public/app.js`: 지금 501로 막히거나 로컬 전용이던 스캔 버튼(현재 `scan()`은 `/api/content-scan`+`/status` 폴링, 916~920줄의 confirm/pause/resume/stop)을 **큐잉+상태폴링+워커 온라인 배지**로 교체(약 70% 재사용 — 폴링 대상만 로컬 라우트→시트 상태칸으로 갈아끼움). `public/index.html` 상단바에 배지 자리 추가.
- 자동시작: `_bat/install-worker.vbs`(검은 창 없이 실행하는 래퍼) + Windows **작업 스케줄러 '로그온 시·숨김'** 등록. `dashboard.bat`·`_bat/content-scan.bat`는 사용자 손에서 은퇴. (크래시 재시작을 위해 작업 스케줄러 '실패 시 재시작' 또는 pm2/nssm 권장.)
  - ★설계 제약: **반드시 로그인 사용자 세션의 프로세스**여야 한다. 진짜 Windows 서비스(Session 0)로 올리면 `headless:false` 크롬이 화면 없이 못 뜨고 로봇인증도 불가.
- **하트비트 배지**(설계 1 접목): 워커가 매 폴링마다 타임스탬프 기록 → 클라우드가 🟢/🔴 표시. (없으면 스캔 눌러도 왜 안 되는지 모름 → 필수.)

**난이도**: 워커 폴러=중, 작업탭 CRUD=소~중, 클라우드 라우트+프론트 재배선=중, 자동시작 포장=소~중.
**손에 잡히는 것**: 스캔이 클라우드 한 창에서 됨(온디맨드 감독) · bat/터미널 사라짐 · 온/오프라인이 눈에 보임.

### 단계 2 — 저녁 예약 무인화 + 납품·설정 클라우드화
- `src/worker.js`에 **내장 저녁 스케줄러**(setInterval + 시각체크) → 저녁창에 업로드 스캔 자동 큐잉. 쿠키 살아있으면 자동, 로봇인증 뜨면 defer+상태칸 기록.
- `src/cloud.js` `LOCAL_ONLY`에서 **`/api/deliver` 제거**(1줄) → 납품 클라우드화.
- 설정: 환율/서비스ID를 set-rate/set-service '작업'으로 워커가 처리하거나 시트 설정탭으로 이관(§5).
- `public/app.js`+`index.html`: 상단에 **"지난밤 스캔: 00:32 · 42/50 확인" / "세션 데우기 필요"** 읽기전용 배지.

**난이도**: 스케줄러=소, 납품 게이트=소, 설정 이관=소~중, 배지=소.
**손에 잡히는 것**: 아침에 열면 밤새 갱신돼 있음 · 납품을 클라우드에서 누름 · 설정을 두 군데 안 고침.

### 단계 3 — 돈을 '작업'으로 + LUN8 템플릿화 (가장 신중)
- **돈-as-작업**: `/api/execute-request`(클라우드, 비번게이트, **LOCAL_ONLY 아님**, 키 불필요) → 시트 execute 작업행 → 워커가 claim → 로컬 SMM키로 기존 집행. **워커측 `EXEC_PW` 재검증 + 주문 멱등키**(중복과금 방지). `/api/plan`도 시트에 최근 팔로워 스냅샷을 요청하는 방식으로 미리보기. `server.js:29`의 `CLOUD?null:key`는 **그대로 둔다**(워커는 non-CLOUD라 키 살아있음). 이후 로컬 대시보드(localhost) 화면을 은퇴("이 창은 이제 안 써요, 클라우드 주소로" 안내).
- **쓰기 경로 field화**(LUN8 선결 — 하이브리드와 무관하게 어차피 필요): 지금 쓰기는 열번호 하드코딩(`app.js` COL_FIELD·`server.js /api/cell`·`Code.gs`). LUN8은 틱톡+인스타 2세트 열이라, `app.js`가 숫자 col 대신 **field명 전달 → server가 `{field}`로 브릿지 → Code.gs가 colmap으로 해석**(Code.gs는 이미 `{field}`면 헤더기반 재해석함 — 서버가 field를 안 보내는 게 유일한 구멍). app.js+server.js+Code.gs 삼단.
- **LUN8을 2번째 캠페인으로**: 멀티플랫폼 읽기모델(계정 객체에 tk/ig 서브필드), 업로드·가드닝 탭 플랫폼 하위탭(state.plat), 캠페인 config에 platforms 플래그. 워커+작업탭 패턴은 **campaignId만 다르게 큐잉**하면 그대로 확장(=다음 캠페인 템플릿). 단 **인스타 자동 스캐너는 아직 없음** → LUN8 틱톡=자동/인스타=수기입(검수·비고·링크는 이미 클라우드 입력 가능). "인스타도 스캔 자동"으로 과약속 금지.

**난이도**: 돈-작업=중(코드는 짧으나 신중도 최상), field화=중, LUN8 멀티플랫폼 읽기=중.
**손에 잡히는 것**: 돈까지 클라우드 한 창(물리안전 유지) · 로컬 대시보드 완전 은퇴 · LUN8이 얹힘.

## 7. 폐기·위험

1. **PC 꺼짐/절전** → 스캔·집행 정지. [완화] 클라우드 하트비트 배지로 '왜 안 되는지'가 항상 보임(미스터리 제거), 절전 해제·저녁 웨이크 스케줄. 사실상 지금도 PC 꺼지면 못 하던 것 — 이제 명확해질 뿐. [수용]
2. **무인 상태 로봇인증/CAPTCHA** → 예약 스캔이 며칠 조용히 멈출 수 있음. [완화] 쿠키 의존 + 막히면 defer + **"세션 데우기 필요" 배지 필수**. 절대 자동해결 안 함. [설계상 한계로 수용] — 이 배지 누락 시 **폐기 지점**.
3. **시트를 메시지버스로 쓰는 한계** — 폴링 지연(20~30초, 활성 세션 2~3초로 완화) + Apps Script 쿼터/일시 HTML오류(브릿지 3회 재시도로 흡수) + 상태셀 쓰기량 증가(스로틀). [폐기지점] 병목되면 버스를 Vercel KV나 '워커가 Vercel 엔드포인트 폴링'으로 교체 — **버스 추상화(`worker-bus.js`)를 얇게 만들어 스왑 가능하게 둘 것.**
4. **돈 중복실행(최고 위험)** — 작업이 두 번 claim되면 이중과금. [완화] 워커 단일인스턴스 락 + 원자적 claim 가드 + **주문별 멱등키** + 기존 persist-before-ack·durable=false·read-repair + 워커측 비번 재검증.
5. **감독 제어 지연** — '스캔 시작/재개'가 클라우드→시트→워커 왕복(수 초). [완화] 활성 세션 적응형 폴링(2~3초). [수용]
6. **두 일꾼/구창 혼란** — 대표님이 옛 로컬 대시보드를 또 열면 두 곳에서 스캔. [완화·폐기지점] 3단계에서 로컬 대시보드 UI 은퇴 안내 + 워커 단일인스턴스 락.
7. **SMM키 배치(명시 요청)** — 채택 A(워커 집행)=삼중방어 유지, 단 PC-온 필요. B(Vercel 집행)=PC 꺼져도 되나 "비번만 알면 지출"로 약화. **A 권장**(§5).
8. **설정 이중 소스** — 자주 바뀌는 환율/서비스는 작업/시트로 단일화, 드물게 바뀌는 구조설정은 개발자 문서화. [잔여 리스크: 소]
9. **Windows 자동시작/Playwright/크롬 업데이트 취약** — 비전문가가 못 고침. [완화] 작업 스케줄러 '실패 시 자동재시작' + (선택) 트레이 '재시작' 버튼 + 로그 열기. ★진짜 서비스(Session 0) 금지 — 반드시 로그온 세션 트레이/작업.
10. **감독 게이트를 클라우드로 안 빼면 약속 붕괴** — confirm/blocked를 로컬 화면에만 두면 다시 두 창 juggle. **반드시 클라우드 노출.**
11. **LUN8 인스타 미구현** — 틱톡만 자동. "다음 캠페인 템플릿"으로 못박기 전에 인스타 수집 계층 계획 필요(별건 대공사, 이 아키텍처와 독립).
