# 02 · LOCAL_ONLY → 클라우드 이전 계획 (money · deliver · config)

> **문서 전용.** 여기 diff/스니펫은 **한 줄도 라이브 코드에 반영하지 않았다.** 아침에 사람과 함께 검토·적용.
> 대상: `/api/deliver` · `/api/plan` · `/api/execute` · `/api/rate` · `/api/service` 를 `src/cloud.js`의 `LOCAL_ONLY`에서 클라우드로.
> 큰 그림(관제탑+무인워커)은 `01_추천_아키텍처.md` 참조. 이 문서는 그 그림 중 **"이 5개 라우트를 어떻게 옮기나"**의 코드 레벨 각론이다.

---

## 0. 3분 요약

| 라우트 | 지금 막는 것 | 클라우드로 옮기는 법 | 키 필요? | 난이도 |
|---|---|---|---|---|
| `/api/deliver` | LOCAL_ONLY 뿐 | **세트에서 빼면 끝** (전부 시트 작업) | ❌ | ★ 즉시 |
| `/api/service` | LOCAL_ONLY + `writeCfg`(로컬파일) | 세트에서 빼기 + **serviceId를 시트 `_state`로** | ❌ | ★★ |
| `/api/plan` | LOCAL_ONLY + 로컬 스캔파일 의존 | 세트에서 빼기 + **팔로워 소스: `scan-latest.json` → 시트** | ❌ | ★★ |
| `/api/rate` | LOCAL_ONLY + `writeCfg` + SMM 잔액조회(키) | fx를 시트로 + **잔액은 시트 캐시에서** | ⚠️(잔액) | ★★★ |
| `/api/execute` | LOCAL_ONLY + 키부재 + `scanAccounts`(실제 크롬) | **워커 큐(권장)** 또는 키 Vercel 이전(트레이드오프 큼) | ✅ | ★★★★ |

**핵심 3줄**
1. **deliver·service·plan 은 키가 필요 없다** — 지금 막혀 있는 건 사실상 `LOCAL_ONLY` 세트의 과보호 + 설정/스캔이 "로컬 파일"이라는 배관 문제뿐. 이 셋은 **시트-상태 전환**만 하면 클라우드에서 그냥 된다.
2. **rate 는 SMM 잔액(=키)이 필요**해서 완전 클라우드화하려면 워커가 잔액을 시트에 캐시해줘야 한다.
3. **execute 만이 진짜 돈**이다. `scanAccounts`가 **실제 크롬 창(`headless:false`)을 띄우므로 Vercel에서 물리적으로 불가**. → 키를 올리지 말고 **집행 요청만 시트에 적고 워커가 대행**(01 문서의 결론)이 정답. 키를 Vercel에 올리는 안(§5)은 물리적 지출차단이 사라지는 대가를 명시한다.

## 1. 지금 왜 막혀 있나 — "3중 차단" 해부

한 라우트가 클라우드에서 안 되는 이유는 최대 3겹이다. 각각을 따로 풀어야 한다.

```
① LOCAL_ONLY 게이트   … src/cloud.js:20-39 세트 + server.js:223 이 501 로 반환
② SMM 키 부재          … server.js:29  const key = CLOUD ? null : …  → 클라우드는 smm=null
③ 로컬 파일 읽기/쓰기  … campaigns.json(writeCfg) · data/c/<id>/scan-latest.json  (Vercel FS는 읽기전용)
```

라우트별로 어떤 겹이 걸리는지:

| 라우트 | ①게이트 | ②키 | ③로컬파일 | 실제로 필요한 배관 변경 |
|---|:--:|:--:|:--:|---|
| deliver | ✔ | · | (읽기만·폴백됨) | 게이트 해제 |
| service | ✔ | · | ✔ (`writeCfg`) | 게이트 해제 + config→시트 |
| plan | ✔ | (있으면 씀) | ✔ (`scanLatest`) | 게이트 해제 + 소스 스왑 |
| rate | ✔ | ✔ (`smm.balance`) | ✔ (`writeCfg`) | 게이트 해제 + config→시트 + 잔액 캐시 |
| execute | ✔ | ✔ (`smm.addOrder`) | (스캔이 크롬 필요) | §5 참조 (워커 or 키이전) |

> **왜 지금이 "이중 안전"인가(현행의 우아함):** `server.js:29` 한 줄 때문에 클라우드는 `smm=null`이다. 그래서 execute/rate는 게이트를 뚫어도 `if (!smm) return 400`에서 다시 막힌다. **이 한 줄이 "URL 알아도 지출 불가"의 물리적 뿌리**다. 옮기기 전에 반드시 이 줄의 의미를 이해하고 건드릴지 말지 결정해야 한다(§5).

## 2. deliver — 제일 쉬움 (게이트만 해제)

### (a) 무엇을 바꾸면 되나

- `buildAccounts` → `getAccountsFromSheet`(브릿지) · `readOrders`(시트모드=브릿지)
- 필터는 시트 열값(음원 19 / 음원구간 20 / 해시태그 21 / 콘텐츠 17)으로만 판정

### (c) 설정 — 해당 없음

## 5. execute — 진짜 돈. 두 갈래와 트레이드오프 ⚠️

### 5-0. 먼저: **Vercel에서 `scanAccounts`는 물리적으로 불가**
`/api/execute`(`server.js:484`)는 집행 직전 `scanAccounts`(`execute-core.js:10`)로 **현재 팔로워를 다시 긁는다**. 그런데 이건 `launchBrowser`(`headless:false`, 실제 크롬 창)를 띄운다. **Vercel 서버리스엔 디스플레이·상주 브라우저·긴 실행시간이 없다** → 어떤 방식이든 execute를 "Vercel 함수 안에서 통째로" 돌리는 건 불가능. 이 사실이 아래 선택을 좌우한다.

---

### 옵션 A — 워커 큐 (**권장**, 01 문서의 결론)
**키를 Vercel에 올리지 않는다.** 클라우드는 "집행 요청"만 시트에 적고, 대표님 PC의 무인 워커(`GARDEN_CLOUD` 없이 도는 로컬 서버 → `key` 살아있음)가 claim해서 기존 `placeOrders`로 대행. 집행 직전 `EXEC_PW` 상수시간 재검증.

- **(a) 바꾸는 것:** 클라우드의 `/api/execute`는 실제 집행 대신 시트 `_worker` 큐에 작업행 append(대상 handles·수량·`confirmToken`). `server.js:29`·`smm.js`·`placeOrders`·`scanAccounts`는 **한 줄도 안 건드림**. (`_worker` 탭·워커 루프 신설은 01 문서 §6 소관)
- **(b) 돈 안전:** "URL 알아도 지출 불가"의 **물리적 뿌리(`server.js:29`)를 그대로 유지**. 클라우드 비번 게이트가 뚫려도 워커가 `pwMatch`(`server.js:33`, `timingSafeEqual`)로 2차 방어. 재스캔도 워커의 실제 크롬으로 그대로 됨 → **신선도 손실 없음**.
- **(c) 설정:** execute 자체는 config 이전과 무관.

이 옵션에선 `/api/execute`를 **LOCAL_ONLY에서 빼지 않는다**(로컬/워커 전용 유지). 클라우드가 새로 노출하는 건 별도 라우트(예: `/api/execute-request`)뿐. → **가장 안전. 절제 원칙과 01 아키텍처에 부합.**

| "URL 알아도 지출 불가" | ✅ 물리적으로 유지 | ❌ **사라짐** — URL+집행비번이면 지출 |
| 유일 방어선 | 물리(키부재) + 비번 2겹 | **집행비번 단 1겹** |
| 키 노출면 | 대표님 PC 1대 | Vercel 환경변수 + 빌드로그·함수로그·서버리스 메모리 |
| 비번 유출 시 피해 | 워커가 막음(2차 검증) | **즉시 실제 지출** |
| 재스캔 신선도 | ✅ 실제 크롬 유지 | ❌ 시트 팔로워(낡음) |
| 되돌리기 | 큐만 무시 | **키 회수 전까지 노출 지속** |

**결론:** 옵션 B는 (i) 물리적 지출차단이 비번 1겹으로 후퇴, (ii) 키가 클라우드 로그/메모리로 노출면 확대, (iii) 재스캔 신선도 상실이라는 3중 비용. **팀 인원이 늘고 URL이 도는 환경(4인팀·북마크 공유)에선 위험이 커진다.** → **옵션 A 권장.** 옵션 B를 택하려면 최소: 강한 무작위 `EXECUTE_PASSWORD`(④ 강제), 실패 레이트리밋/락아웃, Vercel Deployment Protection(팀 SSO)으로 URL 자체를 비공개화, 키 유출 시 smmkings 키 즉시 재발급 런북.

**(c) 신선도 문제:** 옵션 B는 집행 전 재스캔이 없어 "시트 팔로워가 1,000 미만"이라는 낡은 근거로 집행할 수 있다. 완화: 집행 대상에 `scannedAt` 신선도 문턱(예: 6h 초과 시 거부) + "N시간 전 값" 경고. 그럴 바엔 워커로 신선하게 긁는 옵션 A가 낫다.

> **이중과금 방어는 두 옵션 다 유지된다** — `placeOrders`(`execute-core.js:73`)의 즉시 persist·주문번호 없으면 배치중단·`writeOrders` durable=false 시 중단, 그리고 시트 `_orders` id 멱등 upsert(`Code.gs:225`). 이 로직은 **건드리지 않는다.**

## 8. 롤아웃 순서 (안전한 것부터 · 각 단계 독립 배포)

1. **Tier 1 — deliver** : `cloud.js`에서 `/api/deliver` 한 줄 제거. 위험 0(전부 시트). ✅ 이번 주 바로.
2. **Tier 2 — config 배관** : `Code.gs` `_state`에 `config` 키(6-1) → 재배포. `state.js`/`store.js` 캐시(6-2·6-3). 아직 라우트는 안 엶(배관만).
3. **Tier 3 — service** : `setService`(§3) + 게이트 해제. serviceOverrides 시트 왕복 검증.
4. **Tier 4 — plan** : 소스 스왑(§4) + 게이트 해제. (선택) 잔액 캐시(4-잔액).
5. **Tier 5 — rate** : fx 시트화(§7) + 잔액 캐시 의존. 워커가 잔액 미러하는지 먼저 확인.
6. **Tier 6 — execute** : **옵션 A(워커 큐) 채택 권장.** `server.js:29`·키·`scanAccounts` **불변**. 클라우드는 요청만 큐잉(01 문서 §6과 합류). 옵션 B는 §5 트레이드오프 결재 후에만.

> 각 Tier는 `LOCAL_ONLY`에서 라우트를 한 개씩만 빼므로 **문제 시 그 한 줄만 되돌리면 즉시 복구**된다.
