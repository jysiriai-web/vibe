## 1. 목적 / 배경

### 1.1 목적
세일즈 매니저가 월별 탭에 **회사/브랜드명만 적어두면**, 도구가 ① 공식 이메일을 찾아 채우고 ② 카테고리(구분)를 분류하고 ③ 제조사·비브랜드를 정리하고 ④ 이미 접촉한 곳을 표시하는 것을 자동화한다. 지금까지 손으로 하던 "리스트 → 이메일 확보 → 분류 → 중복 거르기"를 반복 실행 가능한 CLI 도구로 만든다.

### 1.2 배경 — 파일럿(6월)에서 확인된 실제 작업 패턴
[`Project/Sales/`](../../Project/Sales/)의 CSV 3종이 매니저가 6월에 **수작업으로** 한 결과물이다. 여기서 도구 설계에 결정적인 사실들이 드러났다:

- **입력 단위는 사실상 '회사명'이다.** `매출순_브랜드타겟_정리.csv`·`6월_리스트_이메일_확보_파일럿.csv`의 1열이 `회사명`/`회사명(매출순)`이고, **LG생활건강·아모레퍼시픽·클리오·애경산업처럼 모회사 단위**로 적고 산하 브랜드(더후·숨37·페리페라…)는 별도 열에 전개했다. → 브리프의 "C열=브랜드명" 가정과 어긋난다. **(선결 결정 D1)**
- **`구분`에 카테고리와 업체 성격이 섞여 있다.** `뷰티(브랜드사)`, `메이크업 ODM`, `제조 ODM`, `화학 소재` 등. 즉 2글자 카테고리 + "브랜드사/ODM" 판정이 한 열에 있었다.
- **이미 접촉한 곳이 대다수다.** `매출순` 64행 중 절대다수가 `기존·발송이력`이고, 진짜 신규 타겟은 소수(오호라·썸바이미·토니모리·스킨79·라엘·터치인솔 등). → **중복 거르기가 탐색만큼 중요**하다.
- **발송 이력은 정형 열이 아니라 자유텍스트(`비고`)에 있다.** `⚠ 2026-02-02 이미 발송 완료(중복)`, `⚠ 2026-02 발송완료(중복 주의)` 형태. → 중복 판정은 정규식으로 비고를 파싱하는 게 메인 경로다. **(선결 확인 D2)**
- **ODM·화학사 함정이 실재한다.** 씨앤씨인터내셔널·코스메카코리아(순수 ODM), 그린케미칼(=KPX, 화학사·화장품 아님), 이미인(글로벌 ODM)에 이메일 찾다가 시간 낭비한 흔적이 있다. → 탐색 전에 거르는 게 최대 절감 포인트다.

### 1.3 무엇을 자동화하면 ROI가 큰가
파일럿 근거상 우선순위는 **(1) 중복/부적합 조기 차단 → (2) 신규 브랜드 이메일 탐색 → (3) 구분 정리** 순이다. "이미 발송"과 "ODM·화학사"를 탐색 전에 거르는 것만으로도 매니저가 가장 많이 버린 시간을 회수한다.

## 2. V1 범위

### 2.1 포함
1. 월별 탭의 회사/브랜드명을 읽어 **이메일을 찾아 채움** (신뢰도·출처 표기 포함).
2. **구분(카테고리)** 자동 분류 — `브랜드 에셋` 마스터 표기에 맞춰 일관성 유지.
3. **제조사·지주사 처리** — 산하 브랜드 전개 또는 (안전하게) 삭제대상 표시.
4. **중복 체크** — `브랜드 에셋` 마스터와 대조해 기접촉/발송이력 표시.
5. **안전장치** — 백업 → dry-run 미리보기 → 사람 확인 → 실제 쓰기.
6. **월별 반복 실행 CLI** — 매달 같은 명령으로 대상 탭만 바꿔 처리.

### 2.2 제외 (상세는 §10)
브랜드 소싱/모집, 메일 발송, A/B 테스트 자동화.

## 3. 입력 · 출력

### 3.1 대상 시트 / 탭
- 단일 구글 스프레드시트. 매달 새 월별 탭(`6월`, `7월`…)에서 작업. **대상 탭은 실행 시 `--tab` 인자로 지정**.
- `브랜드 에셋` 탭 = 마스터(약 2,500행, 발송/회신/성사 이력 포함). **읽기 전용 참조**. 도구는 여기에 절대 쓰지 않는다.

### 3.2 열 구조 — 가정 vs 실제 (⚠ 권한 확보 후 검증 필요)
브리프의 가정은 **B=구분 / C=브랜드명 / D=연락처(이메일)**. 그러나 파일럿 CSV는 `회사명 / 구분 / 확보이메일 / 출처 / 신뢰도 / 영업적합도 / 비고`(7열)로, **회사명 우선 + 더 많은 열** 구조다. 실제 월별 탭과 마스터의 헤더는 아직 못 봤으므로, **읽기 권한을 받는 즉시 헤더행을 읽어 매핑을 확정**한다(선결 액션).

**열 매핑 안전장치**: 열 위치는 코드 상수(`config.py`)로 고정하되, **첫 실행 시 헤더행을 읽어 가정과 일치하는지 자동 검증**하고 불일치하면 경고 후 중단한다(엉뚱한 열에 쓰는 사고 예방).

### 3.3 열 계약(Column Contract) — 보조열 통합 스펙 **(D4 확정 ✅: 별도 열 신설 + 작업 후 자동 숨김)**
교차검토에서 가장 큰 충돌은 4개 영역이 각자 다른 보조열(메모열/중복 4열/제조사 F·G·H/구분 메모)을 정의해 **같은 물리 열을 서로 다른 의미로 점유**할 위험이었다. → PRD에서 **단 한 번** 열 배치를 못박는다. 각 영역은 "자기 열에만 쓴다"가 안전 불변식이다.

> **자동 숨김**: 매니저가 평소 시트를 볼 때 헷갈리지 않도록, 도구는 작업(`--apply`) 완료 후 **보조열(E~I)을 자동으로 숨김 처리**한다(구글시트 열 숨김 — `updateDimensionProperties hiddenByUser=true`, gspread `batch_update`로 1콜). 값은 그대로 남고 화면에서만 접힘. `--show-cols` 플래그로 다시 펼칠 수 있다.

| 열 | 의미 | 쓰는 주체 | 비고 |
|---|---|---|---|
| (기존) | 회사명/브랜드명/구분 | 사용자 입력 | 도구는 구분(B)만 `--clean`에서 건드림 |
| D | **이메일 (대표 1개, SoT)** | 이메일탐색 | 발송 자동화가 그대로 읽는 깨끗한 값 |
| E | 신뢰도 (높음/중간/낮음) | 이메일탐색 | |
| F | 근거·출처·라벨 (`[개인메일]` 등) | 이메일탐색 | |
| G | 중복상태 (enum) | 중복체크 | `중복-성사/회신/발송/기접촉/유사-확인필요/신규` |
| H | 이력요약 (한 줄) + 마스터행 | 중복체크 | 예: `2026-02 발송완료 / 무회신 (행1342)` |
| I | 제조사/처리상태 | 제조사처리 | `전개완료-모회사/전개생성/삭제대상/검토필요…` |

> 위 배치는 **제안값**이다. 실제 월별 탭에 이미 쓰던 열(파일럿의 출처·영업적합도 등)이 있으면 그 관행에 맞춰 조정한다. "별도 열을 새로 둘지 / 기존 6월식처럼 한 열에 섞을지"가 D4 결정의 핵심이며, **6월 탭이 망가진 원인이 '구분 열에 메모 혼입'이었으므로 별도 열 분리를 강력 권장**한다.

### 3.4 입력 단위 규약 — 회사명 vs 브랜드명 **(D1 확정 ✅)**
**표준은 "1행 1브랜드명"**. 단, 입력된 항목(a)이 **제조사/지주사이고 산하 PB 브랜드(b·c)가 있으면 → a 행은 제거하고 b·c를 각각 행으로 추가**한다(아래 §4.3 전개 규칙). 즉 매니저가 `클리오`(모회사)라고 적으면 도구가 `클리오·페리페라·구달` 행으로 바꿔 준다. 중복매칭은 브랜드 우선·회사명 보조로 양쪽 수용.
> a 행 제거는 "삭제"이므로 **백업 → dry-run 미리보기 → 사람 확인** 안에서만 일어난다(§6).

## 4. 핵심 로직

### 4.0 처리 파이프라인 — 단일 게이트 순서 (교차검토 정본)
6개 영역이 각자 "내가 먼저 돈다"고 가정해 충돌했다. 한 행에 대해 아래 **고정 순서**로 처리한다. 앞 게이트에서 종결되면 뒤 단계(특히 가장 비싼 이메일 탐색)는 돌지 않는다.

```
STAGE 0 (실행 1회):
  0.1 헤더 자동검증 — 열 매핑이 가정과 맞는지 확인, 불일치 시 중단
  0.2 마스터 1회 로드 → 인덱스 3종 동시 구축
        brand_index / company_index / canonical_dict(+alias)
        (중복·구분·제조사 영역이 같은 1회 로드를 공유 — 재로드 금지)
  0.3 작업 탭 1회 read (get_all_values) → 메모리

STAGE 1 (행 단위, 쓰기 없음 → ChangePlan 누적):
  게이트 A  정제(Clean)     : 빈 행 표시 / 구분열 메모 분리 / 이름 정규화
  게이트 B  중복(Dedup)     : 마스터 대조. 확정 중복이면 ★조기종료(탐색 스킵)
  게이트 C  제조사 판별     : score≥60 → 전개 or 삭제대상 / 30~59 → 검토필요
  게이트 D  구분 분류       : canonical 사전 안일 때만 자동, 아니면 공란+검토
  게이트 E  이메일 탐색     : 위 게이트 통과한 '순수 신규'만 도달

STAGE 2 (안전 커밋, 쓰기 영역 단독 책임):
  2.1 dry-run 기본 — ChangePlan을 표/CSV/MD로 출력 (쓰기 0)
  2.2 --apply 시 — 백업 → 확인게이트 → batch_update → state 기록
  2.3 행 삭제/전개는 별도 --purge-confirmed 에서만, 역순 삭제
```

**왜 이 순서인가**: 비용 0인 종결자(중복·부적합)를 가장 비싼 탐색 앞에 둔다. 파일럿의 시간낭비 1위가 "ODM·화학사에 메일 찾다 실패", 2위가 "이미 발송을 뒤늦게 발견(PONPISH·닥터지·AHC)"이었다. **중복·부적합 판정의 단일 진실원천(SoT)은 각 전담 영역(B·C 게이트)**이며, 이메일 탐색은 그 결과를 읽어 조기종료만 한다(중복 로직 중복구현 제거).

### 4.1 정제 (Clean) — 게이트 A
- 회사/브랜드명, 이메일 모두 빈 행 → `FLAG_EMPTY`로 **표시만**(자동 삭제 금지).
- 구분(B)열 값이 카테고리(2글자 내외)가 아니라 처리 메모(예: "전화만확인")면 → **별도 메모열로 이관**하고 B는 분류 단계에서 재추론. (6월 탭 오염의 원인을 정리)
- 이름 정규화: 괄호 한·영 분리(`오호라(ohora)`→`{오호라, ohora}`), 법인격·접미 제거(`㈜`·`코리아`·`글로벌`), 공백·기호 제거, 소문자화, NFC 정규화.

> 핵심: **매 실행 STAGE 1 진입 전 인라인 정제**가 선행된다(중복체크의 카테고리 교차검증이 오염 입력에 흔들리지 않도록). `--clean` 모드는 6월 같은 대규모 복구용 별도 옵션.

### 4.2 중복 체크 — 게이트 B (마스터 대조)
**목표**: PONPISH·닥터지처럼 "이미 발송"을 자동으로 잡아 탐색 전에 거른다. **자동 삭제는 절대 안 함, 표시만.**

**매칭 (3단 캐스케이드, 위에서 걸리면 멈춤)**:
| 단계 | 방법 | 판정 | 신뢰도 |
|---|---|---|---|
| ① 정확매칭 | 정규화 키 교집합 | 확정 중복 | high |
| ② 회사명 보조 | 회사명 키 일치 | 그룹 중복(같은 회사·다른 브랜드) | medium |
| ③ 퍼지매칭 | `token_set_ratio` + 길이가드 | 유사-확인필요 | low |

**퍼지 길이가드(한글 오탐 차단)** — `≥6자: ≥88` / `4–5자: ≥92` / `≤3자: 퍼지 끔(정확매칭만)`. 예: `데이지크 vs 데이지`, `시드물·톤28·야다·삐아`(3자 이하) 보호. **(결정 D13: 임계값 — 실데이터 2,500행 확보 후 1회 튜닝 필요한 잠정값)**

**이력 표기 (마스터→끌어오는 범위)**: 상태 등급 1개 + 한 줄 요약만 (우선순위 **성사 > 회신 > 발송 > 기접촉**). 파일럿처럼 정형 열이 없고 `비고` 자유텍스트가 SoT일 가능성이 높으므로 **정규식 파싱이 메인 경로**:
```
m = re.search(r"(\d{4})[-.]?(\d{2}).*(발송|회신|성사)", 비고)
# "⚠ 2026-02-02 이미 발송 완료" → 중복-발송 / "2026-02 발송"
```
**(결정 D12: 끌어오는 범위 — 상태+한줄 권장)**

**오탐 방지**: 퍼지는 절대 자동확정 안 함(파랑 '유사-확인필요'로만). 회사명 보조매칭은 '그룹 중복'으로 약하게(빨강 아님) — 본사 1회 발송으로 계열 전체를 죽이면 기회손실. 카테고리 교차검증으로 동명이인(그린케미칼=화학사) 1차 필터. **(결정 D11)**

**강도 차등**: `중복-성사`=진빨강 `★재접촉 금지`, `중복-회신`=주황, `중복-발송`=노랑. 성능: 마스터 1회 로드 → 역색인(dict) O(1) 조회. 퍼지는 정확·회사명 매칭 실패한 소수 행에만.

### 4.3 제조사·지주사 처리 — 게이트 C
**제1원칙: 도구는 행을 물리적으로 지우지 않는다.** 모든 비브랜드 처리는 **상태열 마킹만**, 실삭제는 사람이 별도 명령으로.

**판별 (신호 가중 합산, `manufacturer_score` 0~100)**:
| 신호 | 점수 | 예 |
|---|---|---|
| 사명 키워드(강): 홀딩스·코퍼레이션·산업·제조·소재·케미칼·테크 | +30 | 그린케미칼·세라믹소재산업 |
| 사명 키워드(중): OEM·ODM·코스메카·바이오·C&C | +15 | 씨앤씨·코스메카 |
| 자사몰 부재 / B2B 전용 시그널 | +25 / +20 | |
| OEM/ODM 본문 명시 | +25 | 이미인(글로벌 ODM) |
| 마스터에 '제조/ODM/모회사' 표기 | **+35** | (가장 강함) |
| 반례: 자사몰 존재(구매 동선) | **−40** | 브랜드사 겸 제조사 구제 |

구간: `≥60` 제조사 확정 / `30~59` 모호(사람확인) / `<30` 브랜드(손 안 댐). **원칙: 과삭제 > 과통과가 더 위험** → 애매하면 통과/사람확인 쪽으로.

**처리 분기**:
- **산하 브랜드 있음 → 전개(대체) ✅D1/D8**: 산하 브랜드를 각 행으로 추가(구분 상속, 이메일은 게이트 E가 채움)하고 **원본 모회사 행은 제거**한다. 신규 행에 `출처=모회사`를 I열에 남겨 추적. 제거는 §6 안전장치(백업·dry-run·확인) 안에서만. 산하 소스는 **마스터 우선**, 없으면 홈페이지 brands(D9). 예: `클리오 → 클리오·페리페라·구달`, `LG생활건강 → 더후·숨37·오휘…`.
  - 멱등성: 같은 탭을 다시 돌려도 이미 전개된 브랜드(b·c)가 존재하면 모회사 a를 다시 제거·재생성하지 않는다(브랜드 norm_key로 존재 확인).
- **순수 제조사(산하 없음) → 삭제대상 표시만**: `삭제대상-순수제조사` + 사유. 회색 서식. 실삭제는 사람이 `--purge-confirmed`(백업+dry-run+역순삭제) 단계에서만. **(결정 D7: 마킹만 권장)** 예: 코스메카코리아·그린케미칼.
- **모호(겸업 ODM) → 자사 브랜드 있으면 전개 + 원본 `검토필요-겸업` 보존**, 없으면 사람확인 큐. 예: 본느(ODM, 자사브랜드 터치인솔만 적합).

### 4.4 구분 분류 — 게이트 D
**핵심 원칙**: 내가 정의한 택소노미가 아니라 **마스터에 실제로 쓰인 라벨을 절대 기준(canonical 사전)**으로 삼아 표기 일관성을 보장한다. 신규 라벨을 함부로 만들지 않는다.

**메커니즘**:
1. 실행 시작 시 마스터 구분열 전체 → `{라벨: 빈도}` 집계 = canonical 사전. 오염 라벨(1~2회 메모성)은 제외.
2. 신규 브랜드의 추정 카테고리 → alias 맵으로 정규화(`화장품/코스메틱`→`뷰티`) → **canonical 사전에 있으면 그 표기 채택, 없으면 자동입력 안 하고 `신규 라벨 후보`로 사람확인**.

기본 택소노미(2글자): `뷰티·패션·리빙·식품·엔터`. 예외 허용: `F&B`(영문 약어)·`펫`(1글자). **금지**: 같은 의미에 `뷰티/코스메틱/화장품` 혼용. 복합 브랜드는 사다리 `뷰티>패션>식품>리빙>엔터`로 단일 라벨 강제(마스터 기존 분류가 있으면 절대 우선). **(결정 D14: 신규 라벨 보류 권장 / D19: 사다리 — 파일럿이 거의 전부 뷰티라 저영향·후순위 / D20: F&B 채택은 마스터 따름)**

### 4.5 이메일 탐색 · 신뢰도 — 게이트 E
순수 신규 브랜드만 여기 도달. 브랜드명 → 도메인 식별 → 메일 수집.

## 5. 시트 쓰기 · 인증 **(결정 필요)**

### 5.1 라이브러리 — gspread 권장 **(결정 D3-a)**
`pip install "gspread>=6.0" "google-auth>=2.0"`. V1 범위가 단순(탭 1개 읽고 D열+보조열 채우기)이라 raw API 제어가 불필요하고 인증·배치쓰기·탭관리가 압축됨. (gspread 6.x는 `oauth2client` 폐기, `google-auth` 사용 — 옛 튜토리얼 코드 주의.)

### 5.2 인증 — 서비스 계정(JSON 키) **(D3 확정 ✅)**
1인 운영 + 반복 CLI(무인 실행) + 시트는 사용자 개인 계정 소유라는 조건에 가장 적합. 서비스계정은 "공유받은 시트만" 건드려 사고 반경이 OAuth 토큰보다 좁다.

> **V2(메일 발송) 확장과의 관계 — 인증이 결정의 발목을 잡지 않는다.** "시트 접근"과 "메일 발송"은 별개 자격증명이다. ① 서비스 계정은 개인 지메일 주소로 발송 불가(워크스페이스+도메인 위임 필요). ② 개인/일반 지메일로 콜드 아웃바운드 대량 발송은 한도·도달률·계정정지 위험으로 부적합. → **실제 발송은 전용 발송 도메인 + ESP(SES/SendGrid 등) 또는 콜드메일 플랫폼의 독립 API 키**로 V2에서 별도 구성한다. 따라서 시트용 서비스 계정 선택이 발송 확장을 전혀 제약하지 않으며, 무인 스케줄 실행 확장에는 오히려 유리하다.

**사용자 1회성 셋업 (2026-06 기준)**:
1. [GCP 콘솔](https://console.cloud.google.com)에서 새 프로젝트 생성 (예: `siriai-sheets-tool`).
2. "API 및 서비스" → 라이브러리 → **Google Sheets API 사용 설정**. (Drive API는 ID/URL로 열면 불필요 — D18)
3. 사용자 인증 정보 → 서비스 계정 생성 (역할 부여 불필요).
4. 서비스 계정 → 키 → **JSON 키 다운로드** → `secrets/service_account.json`. (재다운 불가, 안전 보관)
5. JSON 안의 `client_email` 복사 (예: `sheet-writer@…iam.gserviceaccount.com`).
6. **대상 구글시트 → 공유 → `client_email`을 '편집자'로 추가**. (마스터가 다른 파일이면 그것도 공유.)

### 5.3 쓰기 방식 — `batch_update` (셀 단위 update 금지)
쿼터: 쓰기 **분당 60회/사용자** 초과 시 429. 셀마다 `update_cell` 루프 = 2,500콜 → 즉시 초과. → **결과를 모아 `batch_update`로 1~수 콜에 flush**, 청크 50~500, 지수 백오프(1·2·4·8s). `value_input_option="RAW"` 고정(`+`·`=` 선두 값이 수식으로 처리되는 사고 방지). 읽기도 `get_all_values()` 1콜로 메모리에 올려 처리.

### 5.4 시트 열기 — ID/URL(`open_by_key`) 고정 **(결정 D18)**
이름 검색(Drive API 필요)을 쓰지 않아, 이름 중복으로 엉뚱한 시트를 여는 사고를 원천 차단.

### 5.5 시크릿 보관
`secrets/service_account.json` (경로는 환경변수 `GOOGLE_SERVICE_ACCOUNT_JSON`로 주입). **`.gitignore`에 `secrets/`·`.env` 필수**. 키가 한 번이라도 커밋되면 GCP에서 폐기 후 재발급.

## 6. 안전장치 (과거 시트 손상 이력 → 최우선)

**4단계 강제: 백업 → dry-run 미리보기 → 사람 확인 → 실제 쓰기.** 어느 단계든 실패하면 쓰기 0건.

### 6.1 백업 (쓰기 전 자동, 예외 없음)
- 모든 `--apply` 직전 무조건. 백업 실패 시 쓰기 전면 중단.
- 대상: 작업 탭 + 마스터(참조 시점 스냅샷). 방식: `get_all_values()` → CSV(`utf-8-sig`, 엑셀 한글 호환).
- 파일명: `backups/{YYYY-MM}/{YYYYMMDD-HHMM}_{탭명}.csv`. 0행이면 "빈 시트 의심"으로 중단.
- (선택) 같은 스프레드시트 내 탭 복제 `ws.duplicate(...)`로 1콜 스냅샷도 가능.

### 6.2 Dry-run → 사람 확인 → 쓰기
- **기본 모드 = dry-run.** `--apply`를 명시해야만 쓰기. **(결정 D15)**
- **ChangePlan**(어느 셀에 무슨 값을 왜 쓰는가)을 만들어 표/CSV/MD로 출력 → dry-run과 apply가 같은 계획을 써서 "미리 본 것 = 실제"가 100% 일치.

```
[DRY-RUN] 7월 탭 변경 미리보기 (실제 쓰기 없음)
 셀  | 브랜드   | 현재값   | 쓸값                    | 동작     | 신뢰
 D14 | 토니모리 | (빈칸)   | hjyoon2104@tonymoly.com | FILL     | 중간
 D15 | 라엘     | (빈칸)   | raelkorea@getrael.com   | FILL     | 높음
 D16 | 닥터지   | (이미)   | —                       | SKIP     |  —
 D18 | 포핀쉬   | (빈칸)   | — 중복:브랜드에셋 발송   | FLAG_DUP |  —
요약: FILL 2 · SKIP 1 · FLAG_DUP 1
```
- `--apply` 시 **탭명을 타이핑해야 통과**하는 확인 게이트. 무인 실행(`--yes`)은 **검토 끝낸 `--plan` 파일 동반 시에만** 허용. **(결정 D16)**

### 6.3 멱등성 · 재실행
- D열에 유효 이메일이 있으면 `SKIP`(덮어쓰기 금지). `old==new`면 쓰기 제외.
- **멱등 키는 행번호가 아니라 `(탭, 브랜드 norm_key)`** — 제조사 전개로 행이 추가되면 행번호 키가 깨지기 때문. 전개 신규행은 **맨 끝 append**(중간 삽입 금지)로 기존 행번호 불변 유지. `state/{탭}_applied.json`에 기록 → 중단 후 재개 시 자동 SKIP.

### 6.4 안전 불변식 (코드로 강제)
- 마스터 `브랜드 에셋`에는 **절대 쓰지 않음**(읽기 전용). apply 대상이 마스터면 즉시 거부.
- 쓰기 범위는 **열 계약(§3.3)의 지정 열만** 화이트리스트. B/C 등 사용자 입력 컬럼은 `--clean`일 때만.
- 각 영역은 자기 열에만 쓴다. 모든 실행은 `logs/`에 (시각·탭·모드·변경건수·백업경로) 1줄 기록.

### 6.5 6월 탭 정리/복구 **(D5 확정 ✅: 매니저 수기 복구 완료 → 도구는 '구분'만)**
6월 탭의 메모 혼입·빈 행·이메일 없는 행은 **매니저님이 이미 수기로 정리 완료**했다. 따라서 도구는 6월에 대해 `--clean`(정리·복구)을 수행하지 않는다. **6월에서 도구가 할 일은 '구분(카테고리) 분류'만**이다(이메일·중복·제조사 단계는 생략 가능, `--only category` 모드).
```bash
python run.py --tab 6월 --only category --dry-run   # 6월: 구분만 미리보기
python run.py --tab 6월 --only category --apply
```
> `--clean` 루틴 자체는 코드에 남겨 두되(향후 다른 탭이 오염될 때 대비), 6월에는 호출하지 않는다.

### 7.2 월별 반복 실행 CLI
```bash
python run.py --tab 7월 --dry-run                       # 1) 미리보기 (기본, 안 씀)
python run.py --tab 7월 --apply --plan reports/...csv   # 2) 검토 후 반영(백업→확인→쓰기)
python run.py --tab 6월 --clean --dry-run               # 3) 6월 정리 미리보기
python run.py --tab 6월 --backup-only                   # 4) 스냅샷만
python run.py --gc --older-than 90                      # 5) 오래된 산출물 정리
```
| 플래그 | 기본 | 설명 |
|---|---|---|
| `--tab` | (필수) | 대상 탭. 미존재 시 즉시 에러 |
| `--dry-run` / `--apply` | dry-run | 미리보기 / 실제 쓰기(백업·확인 강제) |
| `--plan <경로>` | — | 검토한 계획만 반영(`--yes` 동반 필수) |
| `--only <단계>` | 전체 | 특정 단계만 실행 (예: `category` = 구분만). 6월용 |
| `--clean` | 꺼짐 | 메모 분리·빈행 정리 (6월엔 미사용) |
| `--purge-confirmed` | 꺼짐 | 삭제대상 실삭제(백업+dry-run+역순) |
| `--show-cols` | 꺼짐 | 자동 숨긴 보조열(E~I)을 다시 펼침 |
| `--yes` | 꺼짐 | 무인(확인 생략). `--plan` 필수 |
| `--limit N` | 전체 | 상위 N행(테스트) |

### 7.3 보관 정책 **(결정 D17)**
권장: **백업 180일 / 리포트·로그 90일** (`--gc`로 일괄). 백업은 복구 최후수단이라 길게.

## 8. 미해결 / 가정 (시트 권한 확보 후 검증할 것)

1. **[선결] 실제 열 구조 미확인.** 월별 탭과 마스터의 헤더를 읽어 §3.2/§3.3 매핑을 확정해야 모든 영역이 정상 동작. → **읽기 권한 공유가 1번 액션.**
2. **[선결] 마스터 이력 스키마.** 발송/회신/성사가 정형 열인지, 파일럿처럼 `비고` 자유텍스트인지. 후자면 정규식 파싱이 메인. (D2)
3. **입력 단위(회사명/브랜드명)** 미확정 — 제조사 전개·중복·분류 전제를 좌우. (D1)
4. **전개 신규행의 2차 패스**: 전개로 생긴 브랜드 행의 이메일·구분·중복을 같은 실행에서 재투입할지 다음 실행에서 처리할지. (권장: 같은 실행 내 append 후 재투입)
5. **외부 탐색 쿼터**: 시트 API(60/분)와 별개로 Google/Naver 검색·스크래핑·MX 조회의 차단·쿼터가 진짜 병목. throttle·캐시(같은 도메인 재방문)·일일한도 정책 필요.
6. **JS 렌더 자사몰** 정적 스크래핑 실패율이 높음 → 브라우저 자동화 도입 여부가 공수에 영향.
7. **인코딩 안전**: 메모·라벨의 `⚠`·`★` 이모지가 CSV 라운드트립/Windows 콘솔(cp949)에서 깨질 수 있음 → utf-8 일관성 명시.
8. **성공 기준 부재**: V1 "완료" 정의(신규 중 이메일 확보율 목표, 미확보율 상한)와 탭당 예상 처리시간/콜수 상한.
9. **동명이인 가드 단일화**: 그린케미칼류 판정을 한 곳(도메인 식별)에서 하고 결과 공유.

## 11. 모듈 아키텍처 & 확장 로드맵 (왜 모듈형인가)

**목표 그림**: 이 도구는 일회성 스크립트가 아니라 **확장 가능한 아웃바운드 시스템의 데이터 기반**이다. 매니저는 이미 [Mailsuite](https://mailsuite.com)로 발송·열람·클릭을 추적 중이고(인플루언서 제안 메일 등), 장기적으로 **발굴 → 발송 → 추적 → 성과분석 → CRM**을 한 흐름으로 잇고자 한다. 그래서 각 관심사를 독립 모듈로 분리해, 시트(데이터 백본) 위에서 단계적으로 붙인다.

### 11.1 데이터 백본 = 구글시트 (이미 그릇이 있다)
마스터 `브랜드 에셋`은 이미 **발송(I)·열람(J)·클릭(K)·회신(L)·미팅(M)·발송일자(N)·회신일자(O)·성사여부(R)** 열을 갖는다. Mailsuite의 "Download CSV"(recipients·opens·clicks)가 정확히 이 데이터다. → **두 시스템이 같은 그릇을 공유**하므로, 통합점은 명확하다.

### 11.2 모듈 맵
| 모듈 (`coldmail/`) | 책임 | 단계 |
|---|---|---|
| `sheets` | gspread 연결·읽기·배치쓰기·백업 훅 | V1 ✅ |
| `normalize` | 브랜드/회사명 정규화(괄호 한영분리·법인격) | V1 ✅ |
| `classify` (+`category_overrides`) | 구분 분류(마스터 canonical 우선) | V1 ✅(6월 적용) |

### 11.3 단계별 로드맵
- **V1 (현재)** — 발굴/정제: 이메일 확보·구분·중복·제조사. 산출물 = 깨끗한 시트.
- **V1.5 — 추적 역동기화 (브리지)**: Mailsuite CSV를 이메일 키로 시트 행에 매칭해 열람/클릭/회신/발송일자 열 갱신. **효과**: 중복판정 정확도↑("이미 열람/회신"), 성과분석 토대, '회신·성사 이력 수동 유지' 자동화. *Mailsuite를 이미 쓰므로 가장 빠른 ROI.*
- **V2 — 발송**: 전용 발송 도메인 + ESP(또는 Mailsuite API). 템플릿 렌더 → 발송 → 발송열 기록. (인증은 시트용 서비스계정과 별개 — §5.2)
- **V3 — 오케스트레이션**: 캠페인/템플릿/성과 대시보드/CRM. Mailsuite가 보여주는 수준의 상위 기능을 시트 백본 위에서.

각 모듈은 **시트를 공통 인터페이스로** 쓰고 독립적으로 붙고 떼어진다. V1.5 이후를 위해 V1의 열 계약(§3.3)·안전 불변식(§6.4)·멱등 키(§6.3)를 지금부터 지킨다.
